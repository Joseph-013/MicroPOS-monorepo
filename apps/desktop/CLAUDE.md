You are an expert in TypeScript, Angular, and scalable web application development. You write functional, maintainable, performant, and accessible code following Angular and TypeScript best practices.

## TypeScript Best Practices

- Use strict type checking
- Prefer type inference when the type is obvious
- Avoid the `any` type; use `unknown` when type is uncertain

## Angular Best Practices

- Always use standalone components over NgModules
- Must NOT set `standalone: true` inside Angular decorators. It's the default in Angular v20+.
- Do NOT set `changeDetection: ChangeDetectionStrategy.OnPush` explicitly. `OnPush` is the default in Angular v22+.
- Use signals for state management
- Implement lazy loading for feature routes
- Do NOT use the `@HostBinding` and `@HostListener` decorators. Put host bindings inside the `host` object of the `@Component` or `@Directive` decorator instead
- Use `NgOptimizedImage` for all static images.
  - `NgOptimizedImage` does not work for inline base64 images.

## Accessibility Requirements

- It MUST pass all AXE checks.
- It MUST follow all WCAG AA minimums, including focus management, color contrast, and ARIA attributes.

## Components

- Keep components small and focused on a single responsibility
- Use `input()` and `output()` functions instead of decorators
- Use `model()` for two-way bound properties with `[(prop)]` syntax instead of pairing `input()` with `output()`
- Use `computed()` for derived state
- Use `linkedSignal()` for state derived from multiple reactive sources that must stay synchronized
- Prefer inline templates for small components
- Prefer Signal Forms (`@angular/forms/signals`) for new forms. They are stable in Angular v22+ and provide signal-based state, type-safe field access, and schema-based validation
- When not using Signal Forms, prefer Reactive forms instead of Template-driven ones
- Do NOT use `ngClass`, use `class` bindings instead
- Do NOT use `ngStyle`, use `style` bindings instead
- Do NOT import `CommonModule`, import only the directives and pipes the template uses, such as `AsyncPipe` or `DatePipe`
- When using external templates/styles, use paths relative to the component TS file.

## State Management

- Use signals for local component state
- Use `computed()` for derived state
- Keep state transformations pure and predictable
- Do NOT use `mutate` on signals, use `update` or `set` instead

## Templates

- Keep templates simple and avoid complex logic
- Use native control flow (`@if`, `@for`, `@switch`) instead of `*ngIf`, `*ngFor`, `*ngSwitch`
- Use the async pipe to handle observables
- Do not assume globals like (`new Date()`) are available.

## Services

- Design services around a single responsibility
- Use the `providedIn: 'root'` option for singleton services
- Prefer the `@Service` decorator over `@Injectable({providedIn: 'root'})` for new singleton services (Angular v22+)
- Use the `inject()` function instead of constructor injection

## Electron / Forge (MicroPOS)

- Renderer: Angular, built to `dist/renderer` (`pnpm build:renderer`). No `<base href>` (a base tag makes the hash router rewrite the URL to the folder, which breaks reload over `file://`).
- Main/preload: `electron/*.ts`, compiled with `tsc -p tsconfig.electron.json` to `dist/electron` (CommonJS). `package.json` `main` points at `dist/electron/main.js`.
- Commands: `pnpm --filter @micropos/desktop start | build | package | make | typecheck | test`.
- DevTools open automatically, detached in a window of their own, whenever the app is not packaged (`!app.isPackaged`, covers `pnpm dev` and `pnpm start`); packaged builds never open them.
- Renderer has no Node access (contextIsolation, sandbox). The preload runs sandboxed and cannot `require` local files, so `build:electron` bundles `electron/preload.ts` into one file with esbuild after `tsc`. Keep the sandbox on; never import Node modules in the preload.
- Angular and `@micropos/core` are bundled into the renderer, so they live in `devDependencies`. `forge.config.js` sets `prune: false` and excludes `node_modules` because Forge's dependency walker can't resolve hoisted workspace deps. When adding native runtime deps (better-sqlite3), they must be shipped and unpacked from the asar; revisit this config then.
- **Installing over the first MicroPOS (Windows):** the earlier app was `micropos` 1.0.0 (Squirrel id `micropos`, `micropos.exe`, data in `%APPDATA%\micropos`: `micropos.db`, `logs/`, `user/logo`, plus Chromium's storage). This app takes the same identity (`productName: "micropos"`, the Squirrel maker's `name: 'micropos'` in `forge.config.js`) so Setup upgrades it in place, and its version must stay **above 1.0.0** (Squirrel launches the highest installed version, so an older number would keep running the old app). `electron/squirrel.ts` answers the installer events (shortcuts made and removed, the app exits); without it Setup would open windows and make no shortcuts. **Old data is wiped once:** `purgeLegacyData` (`electron/legacy-data.ts`, called first thing in `main.ts` for packaged builds only) removes everything in the user data folder unless it holds the marker `micropos-data.json`, then writes the marker; Chromium's own storage is cleared through `session.defaultSession.clearStorageData()` after that. From then on the folder is left alone. To force another clean start on a future install, raise `DATA_GENERATION`. Not run in development (the dev database lives in `local-data/`). Not testable on Linux beyond the unit tests (`legacy-data.spec.ts`); try a real Setup.exe on a Windows machine that has the old app.
- **Building (`pnpm make`, which runs `electron-forge make` after the build):** Linux only for now (`LINUX_MAKERS` in `forge.config.js`: a zip and an rpm; add `WINDOWS_MAKERS`, the Squirrel installer, when building on Windows; the deb maker needs `dpkg`). Output: `out/make/rpm/x64/micropos-<version>-1.x86_64.rpm` and `out/make/zip/linux/x64/MicroPOS-linux-x64-<version>.zip`; the unpacked app is `out/MicroPOS-linux-x64/micropos`. The scoped package name is not usable as a file name, so `executableName` and the rpm `name`/`bin` are set to `micropos`. `rpm-spec.ejs` is a copy of the maker's spec with one fix (rpm 6 builds in a subfolder, so `%install` copies from `%{_topdir}/BUILD/usr`). The main process imports values from `@micropos/core`, so `forge.config.js` ships its `dist` (`RUNTIME_MODULES`); a new runtime import that is not listed there crashes the packaged app with "Cannot find module". **Smoke-test a build** with a throwaway data folder, never the real one (the first start wipes it): `out/MicroPOS-linux-x64/micropos --no-sandbox --user-data-dir=$(mktemp -d)`.

Without it the taskbar shows Electron's stock icon. Check with `WAYLAND_DEBUG=1 out/MicroPOS-linux-x64/micropos --no-sandbox --user-data-dir=$(mktemp -d) 2>&1 | grep set_app_id`. **Development has its own app id**, `micropos-dev` (`app.setDesktopName` in `main.ts`; otherwise the dev window announces `micropos` and the taskbar shows the icon of whatever MicroPOS is installed, e.g. the stock Electron one from an old rpm), and `scripts/dev.mjs` writes a hidden launcher entry `~/.local/share/applications/micropos-dev.desktop` (Linux only, every start; `Icon=` the repo's `assets/icon.png`; it asks KDE to rescan with `kbuildsycoca6` when available), so the dev taskbar icon is the app icon. If it still shows the old icon after the first start, log out and in once, or run `kbuildsycoca6 --noincremental`. The window title is fixed to **MicroPOS** (`page-title-updated` is cancelled in `main.ts`; the customer display's is "MicroPOS customer display").
- **Name, icon and menu:** the display name is **MicroPOS** (`productName` in `package.json`; the file names stay lowercase: executable and rpm package `micropos`, Squirrel id `micropos`). The app icon is the nav rail's collapsed mark (`lucideComputer`) on the dark theme background: `assets/icon.svg` is the source, `icon.png` (512) and `icon.ico` (multi-size) are generated from it with ImageMagick (`magick -background none -density 384 assets/icon.svg -resize 512x512 assets/icon.png`, then `magick assets/icon.png -define icon:auto-resize=256,128,64,48,32,16 assets/icon.ico`) and committed; `forge.config.js` uses it for the packaged app, the rpm and the Windows setup, and `main.ts` for the window. The installer and the app work unsigned; Windows SmartScreen shows "Windows protected your PC" on first run of a downloaded Setup.exe (More info, then Run anyway), and an antivirus can occasionally flag it. - Not containerized (see `.dockerignore`).

## UI conventions (MicroPOS)

- Copy: titles and labels are short, professional, sentence case ("Checkout", "Sales Orders"). No descriptions, subtitles or helper text unless critically necessary, e.g. confirmation dialogs.
- Anything pressable (buttons, checkboxes, switches, radios, tabs, options, menu items, links, selects) shows the pointer cursor and anything disabled shows not-allowed: a base rule in `src/styles.css` (Tailwind 4 leaves buttons on the arrow), so components need no `cursor-pointer` of their own. A utility class beats that rule, so a pressable component must never set `cursor-default` (the Spartan helm components did, and were changed to `cursor-pointer`; check this after adding or regenerating one).
- Shape: square and boxy everywhere. No `rounded-*` classes; the theme radius is 0. Only radio buttons stay circular (as in the design). Dialogs are square with the `blueprint` corner marks; only confirmation (alert) dialogs carry a description.
- Scrollbars are styled globally in `styles.css` (slim, square, no arrows); don't restyle them per component.
- Keep borders minimal: corner marks (`blueprint`) are for large panels only. Repeated items (grid cells, list rows) get a single hairline border with no marks and no outlined tags (`before:hidden`, `tagNeutral`).
- Destructive actions (Delete, Clear, Remove) use the `destructive` variant on the button, the menu item (`variant="destructive"`) and the confirming alert-dialog action. Restore and other safe confirmations stay default. Exception: the Clear button beside Complete sale on Checkout stays neutral (outline) so it does not draw the eye next to the main action; its confirmation dialog's Clear action is still destructive.
- Space is at a premium: keep page padding tight (main content uses `p-3`) and put titles close to the edges.
- Styles are plain CSS (Tailwind v4 via PostCSS), not Sass; global styles live in `src/styles.css`.
- Kiosk behavior: text selection is off app-wide (`html { user-select: none }` in `styles.css`). Inputs and textareas stay selectable; opt other text in with Tailwind `select-text` or `select-all` (order numbers, receipt text, error messages).
- **There is no minimum window size** (the "window too small" overlay was removed so phones and tablets paired over the network can use the app). The layouts were designed for about 1024 px wide and are not yet tuned for narrow screens: tables and wide panels scroll sideways until the mobile layouts are done.
- Touch sizing lives at the root: `--control-height` (44px), `--control-height-sm` (36px), `--control-height-lg` (56px) and `--popup-offset` in `src/styles.css`. Buttons, inputs, selects, tabs, and menu/list rows read them, so one edit resizes the app. Do not set `h-*`/`size-*` on a control in a page; use the component's `size` input (`size="lg"` for primary actions). New or newly generated Spartan components must use these variables instead of fixed heights.
- **Settings page** (`pages/settings.ts`): one centred column (`mx-auto max-w-xl`) with a **search box** on top and a Spartan **accordion** (`hlm-accordion type="multiple"`, several sections open at once; Account starts open, the rest closed, and the user's own opening and closing is kept while the page lives). Every section is an `app-settings-section` (`pages/settings-section.ts`; a section is a component of its own when it has logic, like `printer-settings.ts`, or inline in the page); section titles are capitalized like page names: "Input", "Customer Display". **Every setting inside a section carries `appSetting="<label>"` (and `settingKeywords="words people might type"`)** on its row, or on the block for a group of fields: that is what the search looks at. While something is typed, only sections whose title or a setting matches are shown (all words must match, ignoring case and accents), a matching section is held open, and inside it only matching settings show (a section whose title matches shows all of its settings); "No settings found" when nothing matches. `SettingsSearch` is a root service the page clears when it closes. **A new setting without `appSetting` cannot be found by search; a new section is `app-settings-section`, not a card.** Order: per-person and per-device sections first (Account, Input, Customer Display), then the shop-wide ones that need a permission (Credit Interest, Credit Alerts, Receipt Printer, Window, Logs, Debug). The accordion is generated Spartan code (`ui/accordion`), triggers carry the pointer cursor from the base rule.
- Required fields: label them with a red asterisk, not "(required)" text: put `data-required` on the `<label hlmLabel>` (styles.css adds the asterisk). Only mark fields that must be filled; optional ones stay plain.
- Forms are draftable: a dialog form that takes more than a moment to fill in saves its progress as a draft (see Form drafts under Products page: debounced save, restored with a "Draft restored" banner, Close instead of Cancel, Reset, cleared on save) so leaving the page or restarting loses nothing. If a form seems too small to need one, ask the user before leaving it out.
- Touch first: keep targets comfortable (nav rail is 3.5rem collapsed with 40px rows).
- **Top bar and navigation drawer** (`core/topbar.ts`, `core/nav-drawer.ts`, `core/nav-rail.*`): a 3rem top bar with the logo on the left and the burger at the far right, **shown on phone-sized screens only** (`hidden max-md:block`; `--topbar-height` is 3rem there and 0 on wide screens, set on the app container; **pages that fill the window subtract it**: `h-[calc(100svh-var(--banner-offset,0px)-var(--topbar-height,0px)-1.5rem)]`). It has **no page title** (every page shows its own). **Wide screens (from Tailwind `md`, 768 px) have no top bar and keep the look as it was: the rail on the left, collapsed to icons, opening on hover or when pinned.** Below it (`NavDrawer.mobile`, a `matchMedia` signal) the navigation moves to the **right** and is hidden (`translate-x-full`, `inert` so it cannot be tabbed into) until the burger opens it as a drawer over the page with a dimmed backdrop; a tap outside, Escape or choosing a page closes it. The rail's host reserves no width on a phone, and the pin button is not shown there.
- Colors and fonts come from `@micropos/theme` tokens (Tailwind classes such as `bg-primary`, `text-muted-foreground`); don't hard-code values.

## Table design

The Products table (`pages/products/`) is the reference; build every data table the same way.

**Layout**
- A CSS grid with table roles (`role="table"`, `rowgroup`, `row`, `columnheader`, `cell`), not a `<table>`, so each row can sit inside `app-swipe-actions`. One column template (`COLUMNS_TEMPLATE`) is shared by the title row, the filter row and every body row. The table has a `min-w-*`; the area around it scrolls both ways and has no side padding (swipe actions stick to its visible edge).
- The header is sticky and has two rows. **Row 1** holds the column titles: each is a button that sorts by that column (click once ascending, again descending) with a direction arrow (`lucideChevronsUpDown` when idle) and `aria-sort`. **Row 2** holds the filter for that column, directly above the data it filters. Example: the Name column is "Name ^" over a text input; the Categories column is "Categories ^" over a select. There is no separate search or filter bar above a table, and the header with its filters stays visible when no rows match.
- Filter controls fit the column: text input for names and codes, combobox or select for categories and status, a from/to date range (native date inputs) for dates, a range for numbers. Text and date filters use `app-filter-input` (`core/ui/filter-input.ts`: a button group, the input joined to an x clear button that is disabled while the field is empty); comboboxes use `showClear` (hidden while on "All"). Filters are compact (the filter row sets `--control-height` to the small size) and have placeholders. Columns with nothing to filter leave their filter cell empty. Date range filters treat a first date as a single day (the end date follows it); change or clear the end to widen it, and a cleared end means "from then on". Filters on different columns combine (AND).
- **Leftmost column is selection**: a checkbox per row, and the title-row checkbox selects every visible row (shows a dash while only some are ticked). The filter-row cell under it holds a **Reset filters** icon button (disabled when no filter is set). Selection counts the rows that match the current filters, on any page: it survives changing pages, Shift ranges follow the filtered list across pages, and a filter never leaves a hidden row selected for a bulk action to hit. The header checkbox ticks (or unticks) only the rows of the current page, shows a dash while only some of them are ticked, and leaves other pages' selections alone; there is deliberately no "select every row on every page" action. Selection works like a file explorer (`RowSelection`, `core/ui/row-selection.ts`): **Ctrl/Cmd + left click** on a row toggles it, **Shift + left click** selects the range from the last row clicked (replacing the selection; with Ctrl too it adds to it), and **Shift + click on a checkbox** ticks the range. A plain click opens the row as before. Ranges follow the filtered, sorted list (across pages).
- Default sort is by created date, newest first; empty values (no SKU, no cost) always sort last. Money columns are right-aligned. Status columns use a badge: `success` (green) for active, `destructive` (red) for inactive, `outline` for deleted.
- Small text for long codes (SKU `text-xs`), muted color for secondary columns, truncate long values.

**Row actions** (every route offers the same actions)
- Bulk buttons appear in the page header when rows are ticked ("N selected", then the actions that apply, then Clear).
- Right-click (or long-press) context menu on the row (**Safari on iPhone and iPad never sends `contextmenu` for a long press**, so `LongPressContextMenu`, `core/ui/long-press-context-menu.directive.ts`, a host directive of `hlmContextMenuTrigger`, opens every context menu on a 450 ms touch hold: it sends the `contextmenu` event at the touch point, drops the browser's own duplicate and swallows the click after the release; moving more than 10 px, as in a swipe or scroll, cancels it; while the finger holds, a slow ripple grows under it over the same 450 ms, skipped with reduced motion); if the row is part of a multi-row selection the action applies to the whole selection (single or bulk). Delete is destructive-styled; menu items that would change nothing are not offered. Status changes read "Set" followed by the badge the row will get (`Set [Active]`, `Set [Inactive]`).
- Swipe left on a row (touch): icon-only action (the shared swipe component; red with a white icon for delete, green for restore). Mouse and keyboard users have the menu and buttons.
- Delete and restore always show a confirmation dialog, whichever route started them. The dialog lists what it is about to act on (`app-confirm-items`: every name, with a secondary detail such as the SKU), for one row as well as for a bulk selection. Status changes and other easily undone edits apply at once with a banner.
- Deleted rows are reached through a "Deleted only" switch in the page header (swaps the list; the normal list never mixes them); they are dimmed, read-only, and can be restored.

**Page headers on a phone** (below `md`): a table page's header wraps (`max-md:flex-wrap`) and its secondary actions (the Show empty / Deleted only switch, Repackage) fold into a **"More actions" dropdown** (`md:hidden`, next to the main action such as Add or Receive stock); the switch label and those buttons carry `max-md:hidden` on wide screens' copies. A new secondary action goes in both places.

**Cards on a phone** (below `md`): a table (`.table-cards` on the `role="table"` element, rules at the end of `styles.css`, unlayered so they beat the desktop utilities) becomes a list of cards, so nothing scrolls sideways and a swipe on a card is only the card's swipe action. Rows are cards: the first column in the admin's order (`data-primary`) is the title beside the selection checkbox, every other cell is one line: the name in a fixed-width column and the value right beside it, left-aligned (so a line is easy to follow), with a faint rule between lines; a cell made of several parts (a number and its unit) stays together. The title and filter rows are hidden until the **Sort and filter** button (in `app-column-config`, phone only; `layout.filtersOpen`) opens them: titles as sort chips, filters stacked under their names. Every cell of a column carries `[appCol]="layout.col('<key>')"` (`AppCol`, `core/ui/table-column.directive.ts`: CSS `order`, `data-label`, `data-primary`); **a new column needs it on all three cells**, and a table root needs `table-cards max-md:min-w-0` and `[attr.data-filters]`.

**Column order (admins)**: every grid table has a **Columns** icon button at the right of its header (`app-column-config`, `core/ui/column-config.ts`, shown only with `settings.manage`) that opens a dropdown listing the columns, each with a drag handle at the right (also arrow keys up/down on the focused handle) to reorder them. Hiding columns is deliberately not built. The order is saved for everyone (`tables.saveColumnOrder`, `settings.manage`; stored in the `settings` table as `tableColumns`, `{ tableId: keys[] }`; `tables.columnOrders` is readable by anyone signed in and loaded by `TableColumnsService`). A page declares `COLUMN_DEFS` (key, label, width) and `layout = tableLayout('<table id>', COLUMN_DEFS, lead, tail)`; the grid uses `[style.--cols]="layout.template()"` and **every cell of a column (title row, filter row, body row) carries `[appCol]="layout.col('<key>')"` (which sets the CSS `order`)**: when adding a column to a table, add it to `COLUMN_DEFS` and give all three cells the order. The selection cell (`lead`) has no order so stays first. Reordering is visual (CSS `order`), so Tab order still follows the DOM. Done for Products, Categories, Inventory, Sales Orders, Customers, Suppliers and Purchases (not the small Users table).

**Paging and highlighting**
- Every table has a footer (`app-pager`, `core/ui/pager.ts`): "26–50 of 120", rows per page (25, 50 default, 100), first / previous / next / last and "Page n of m". It is offset paging over the already filtered and sorted list (`Pager`: page `n` = rows `n * size` to `(n + 1) * size`), and goes back to page 1 when a filter, the sort or the page size changes. All data is still loaded into the renderer and sorted and filtered there, which is fine for the catalog tables; when Sales Orders gets big, move its sort, filter and paging into the main process (`orders.list({ ..., offset, limit })` returning rows and a total) without changing the footer.
- **Highlight, don't select:** a row that is the target of a link or of the dialog being shown gets `.row-target` (tinted with an inset accent bar; `styles.css`), separate from the selection checkbox. Put the class on the `role="row"` element **inside** `app-swipe-actions`, not on the outer wrapper: the swipe component paints an opaque `bg-background` over the wrapper, which hides a tint there (selected rows use `bg-muted` on the inner row for the same reason). Each page has a `target = rowTarget()` (`core/row-target.ts`) set when a dialog opens for a row (edit product or category, view an order, adjust a batch) or a link names one. The highlight lasts 6 s (`ROW_TARGET_MS`) and then goes away on its own; targeting a row again restarts the clock. Rows carry `data-row-id` on the wrapper; `scrollToRow` (`core/row-target.ts`) scrolls to it once it has rendered, retrying for up to 2 s.
- **`?highlight=<row id>`** on a table page shows the page holding that row and highlights it (`Pager.showItem`); filters that hide the row are cleared first. Implemented on Sales Orders (the order dialog's external-link button goes to `/orders?highlight=<order id>`); the parameter is removed once used. `?view-sales-order=<id>` and `?edit-product=<id>` also show the target's page and highlight it.

**Motion**: rows fade in and out (`animate.enter` / `animate.leave` with `row-enter` / `row-leave`, 0.1 s), and a row whose data changed flashes the accent color briefly (`row-flash`); all in `styles.css`. Rows do not animate on the first load.

## Local storage

- Use `StorageService` (`src/app/core/storage/`), never `localStorage` directly. Keys are namespaced `micropos.*`, values are JSON, reads fall back safely.
- Changing the shape, name or meaning of a stored value requires a new entry in `storage.migrations.ts` (append-only, next version number, idempotent). Never edit a shipped migration.
- Only per-device preferences belong here (nav pin, on-screen keyboard...). Business data goes in SQLite via the main process. The **theme** (light, dark, system) is chosen in Settings > Account and is per user: `ThemeService` keeps each person's choice under `theme.<employee id>` (and the last choice under `theme`, which the lock screen and anyone who has not chosen use). There is no theme control in the nav rail. **When it loads:** `App` injects `ThemeService` at launch (it used to start only when Settings was opened, so the theme was missing until then and shifted on a reload), a small script in `index.html` applies the `dark` class before the first paint from `micropos.themeApplied` (the mode in use, written by the service whenever it applies one), and the service starts from that key, so a reload or a dev rebuild keeps the same theme instead of flashing light and shifting once sign-in is known.
- **Last page:** `LastRoute` (`core/last-route.ts`) saves the last URL shown (query parameters included, so an open dialog and its draft come back) under `lastUrl`, and the `''` route redirects to it at start (Checkout when there is none, or when the saved route no longer exists, e.g. a development-only page; a saved URL that fails to match any route, such as a deeper path removed by an update, is forgotten and Checkout opens). The customer display is never saved. No migration: a missing value means Checkout.
- Keep the app `name` and the `file://` origin stable: both determine where storage lives.

## Barcode scanner

- **Scale labels:** Checkout first looks for a product whose barcode/SKU equals the scanned code; failing that, a 13-digit code starting with 2 with a valid check digit is read as a scale label (`parseScaleBarcode` in core, layout `2 PPPPP 0 WWWWW C`: PLU and weight in grams). The weighed product whose code is that PLU is added with that weight (converted to its unit); a second label for the same product adds to the line. Labels that carry a price instead of a weight, or other layouts, need a store-level layout setting (not built). Everywhere else a scan looks a product up (Products, receiving stock, repackaging, receiving a purchase) a scale label stands for the PLU inside it (`productCodeOf` in core), so scanning one finds its product; only Checkout reads the weight.

- USB keyboard-wedge scans are detected in the **Electron main process** (`electron/scanner/`), in front of the page, so a stray scan can never reach the UI. `attachScanner(win)` (called in `main.ts`) hooks the window's `before-input-event`. `ScanGate` holds every printable key back for one speed threshold (35 ms): if the burst turns out to be a scan (`BurstDetector`: min 3 chars with Enter, 6 without; printable ASCII so 2D payloads work) the held keys are discarded, the closing Enter is swallowed and the code is sent to the page as `scanner:scan`; if it was a person typing, the held keys are replayed to the page in order (`sendInputEvent`), so typing is delayed by at most 35 ms. Shortcuts (Ctrl/Alt/Meta), Tab, arrows etc. pass straight through. Shift/CapsLock never disturb a burst.
- Because the scan's keys are never delivered, nothing can leak: no text in fields, no Space pressing a focused button or checkbox, no Enter reopening a dialog trigger, whatever has focus. The renderer has no keyboard listener for scans any more.
- The renderer (`src/app/core/scanner/`): `ScannerService` (started at the root) subscribes to `window.micropos.scanner.onScan` and only decides who gets the code. Without the Electron bridge (plain browser) no scans arrive. `scanner.enabled` is forwarded to the main process (`scanner.setEnabled`); off lets scanner keys through as ordinary typing.
- **Hooks:** `ScannerService.addHook(fn)` lets something take a kind of code before the claims, wherever the till is (the receipt's order QR, `OrderQrScan`); `fn(code)` returns true when it took it. A focused `appScanInput` field still comes first.
- Take control with a claim: `claimScanner(handler)` in a component or dialog (released on destroy), or the `appScannerClaim` directive with `(scan)`. The newest claim gets scans; releasing it returns control to the previous one. A handler can return `false` to pass a scan down.
- To let a text field receive scans (e.g. a barcode lookup), put `appScanInput` on it (`(scan)` emits the code). While it is focused the scan sets its value to the code (firing `input`), and claims do not get that scan. Fields without it never receive scanned text.
- Tests: the gate and detector are pure and tested with a fake clock in `electron/scanner/*.spec.ts` (`pnpm test:db`). In page specs, stand in for the scanner with `TestBed.inject(ScannerService).receive(code)`. Note that CDP and `sendInputEvent` key events bypass `before-input-event`, so the main-process path can only be exercised with real keyboard input.
- Changing anything under `electron/scanner/` needs a restart of `pnpm dev`.
- `KioskFocusService` stops mouse/touch presses on buttons from taking focus (clicks still work), so focus stays on the field a scan should go to. Add `data-allow-focus` to anything that must take focus.

## Database (SQLite + Drizzle)

- Main process only (`electron/db/`); the renderer reaches it over IPC. Schema is one file per table in `electron/db/schema/` (exported from `schema/index.ts`). Conventions: UUIDv7 text ids (`uuid7()`), money in integer cents, timestamps as epoch milliseconds, soft delete via `deleted_at` on catalog/people tables, orders are never deleted (void or refund instead), a partial unique index for any unique field on a soft-deletable table, and an index on every foreign key.
- Change workflow: edit the schema, run `pnpm db:generate` (writes a new SQL file in `electron/db/migrations/`; commit it, never hand-edit a shipped migration). The history was squashed into one `0000` migration before any release, so a database made earlier (e.g. the dev one) must be rebuilt with `pnpm db:migrate --fresh --seed`; once a build ships, migrations are append-only again. Pending migrations are applied automatically when the app opens the database; packaged builds ship them via Forge `extraResource`.
- Commands (work from the repo root or `apps/desktop`; modeled on Laravel): `pnpm db:migrate` applies pending migrations; `pnpm db:migrate --fresh` drops every table, migrates from scratch and creates one admin account; `pnpm db:migrate --fresh --seed` also runs the factories; `pnpm db:seed` runs the factories only (refuses a database that already has a catalog); `--database=<file>` targets another file. The default file is `apps/desktop/local-data/micropos-dev.db`, which is also what the unpackaged dev app opens (packaged builds use the per-user data folder). Close the dev app before `--fresh`, then restart it.
- The bootstrap admin (`seeders/admin.seeder.ts`) is employee number `1001`, PIN from `MICROPOS_ADMIN_PIN` or the dev default `1234`. Dev tooling only: the CLI is not shipped in packaged builds.
- PINs are stored only as scrypt hashes (`electron/auth/pin.ts`).

### Factories and dummy data

- `electron/db/factories/` builds consistent dummy data (faker): employees, catalog, sales with lines and payments, voids, refunds, login sessions, audit entries, settings. Dev-only: not shipped in packaged builds and never imported by production code paths.
- **When the schema changes, check the factories.** New or renamed columns, new tables, changed constraints or enums (employee roles, order statuses, payment methods) usually need a matching change in the builders (`*.factory.ts`) and in `seed.ts` (insert order, FK order, totals that satisfy CHECK constraints). Update them in the same change.
- **Known barcodes:** the seeded catalog starts with one product per code in `factories/known-barcodes.ts` (a printed test sheet of real EAN-13 codes), with faker names, prices and tracking, followed by the hand-written sample products and random extras. The `480...` codes are the product barcode as they are. The `2...` codes are variable-weight scale labels (`2 PPPPP 0 WWWWW C`): the product is seeded as a weighed one (kg) whose code is the 5-digit PLU without leading zeros (`scalePlu`), not the whole label. Add new sheet codes to that file (a test checks every check digit).
- Verify with `pnpm test:db` (runs migrations on a temp database, seeds it, and checks constraints, totals, payments and foreign keys). Add a test for any new rule.
- Seeding is done through the commands above (`--seed`). Factories reuse the existing admin instead of creating another. Dummy sign-ins: `1001` (admin), `1002` (manager), `1003`+ (cashiers); dummy PIN `1234`.

## IPC bridge (renderer to database)

- The renderer never touches SQLite. It calls `window.micropos` (typed as `DesktopApi` in `@micropos/core`), exposed by the sandboxed preload (`electron/preload.ts`), answered by `ipcMain.handle` handlers in `electron/ipc/`. In Angular, inject `DESKTOP_API` (`core/api/desktop-api.ts`) or a service built on it, such as `CatalogService`; tests provide a fake `DESKTOP_API`.
- Adding a call: (1) add the DTO and method to `packages/core` (`catalog.ts`, `desktop-api.ts`) and rebuild core; (2) write the query as a plain function in `electron/db/queries/` and test it in `db.spec.ts`; (3) add the channel to `electron/ipc/channels.ts`; (4) register the handler in `electron/ipc/index.ts`; (5) expose it in `electron/preload.ts`; (6) use it from a service. Handlers stay thin: validate input, call the query, return plain data.
- Contract version: `DESKTOP_API_VERSION` (`@micropos/core`) and `API_VERSION` (`electron/ipc/channels.ts`) must be equal (a test enforces it). Bump both when a call or payload changes in a way an older main process cannot handle. At startup the page asks the main process for its version (`DesktopApiGuard`); on a mismatch, or an old main that does not answer, a persistent banner says to restart the app. In development the page hot-reloads but the main process does not, so **restart `pnpm dev` after any change under `electron/`** or to `packages/core` (the dev script clears the Angular dev-server cache on start, which otherwise keeps a stale pre-bundled copy of core and shows "out of date" even when both sides match).
- DTOs in `@micropos/core` are types only (the CommonJS main process imports them with `import type`).
- For the dev app, run `pnpm db:migrate --fresh --seed` first so there is data to read.

## Products page

- `pages/products/` lists every live product (active or not) from `ProductsService` (`window.micropos.products.*`, queries in `electron/db/queries/products.ts`); Checkout still reads active products only through `CatalogService`. Rows open an add/edit dialog (`ProductForm`, opened with `HlmDialogService`); Delete asks first and soft-deletes.
- Validation lives in the main process (`sanitizeProductInput`, duplicate SKU/barcode check); a rule violation returns `{ ok: false, field, error }` and the form shows it under that field. Prices are typed in pesos and stored as cents (`core/money-input.ts`).
- **Sold by / weighed products:** `products.unit` is `each` or a weight unit (`kg`, `g`, `lb`, `oz`); the price and cost are per that unit and the checkout quantity is the weight (decimal, stored as thousandths). Adding a weighed product at checkout opens its weight field at once; adding it again edits that weight instead of adding a unit. A draft line carries its `unit`.
- **One code field:** barcode and PLU are one column, `barcode` (shown as "Barcode / PLU" in the table and filter; the product form labels it "Barcode" for a product sold by Each and "PLU" for one sold by weight): packaged goods have an EAN, loose goods a short PLU, rarely both. SKU stays separate (your own stock code). No product needs a code (a weighed one without can still be tapped at checkout, it just cannot be scanned or keyed in). Seeded counted goods get an EAN, weighed ones a 4-digit PLU. In the Products table a PLU (4 or 5 digits, `isPlu` in core) is shown in italics and a barcode in regular type. Reading variable-weight barcodes (prefix `2` + item code + weight) is not built yet.
- **Delete and restore:** a leftmost select column (header checkbox selects every visible row) feeds bulk Delete / Restore buttons in the page header; a row can also be deleted or restored from its right-click menu or by swiping it left. All routes go through one confirmation dialog (`ask()` in `products.ts`), always shown. Acting on a row that is part of a multi-row selection applies to the whole selection. Restore skips a product whose SKU or barcode a live product has since taken and names it in a banner. The "Deleted only" switch swaps the list to just the deleted products (and the normal list hides them); deleted rows cannot be edited.
- The Products table is a CSS grid with table roles (`role="table"`, `row`, `cell`), not a `<table>`, because a row has to be wrapped in `app-swipe-actions` to be swipeable and `<tr>` cannot be wrapped. The title row, filter row and body rows share one column template (`COLUMNS_TEMPLATE`).
- **Scanner:** the page claims the scanner: a scan resets the filters and sets the Barcode / PLU filter to the code, with a warning banner when nothing matches. While the product form is open it claims the scanner instead and a scan fills its Barcode / PLU field (typed straight into it when that field is focused via `appScanInput`, and put there from any other field of the form, never into the name or SKU), so the table behind never changes and barcodes need no manual typing. The row's Enter handler still ignores a `defaultPrevented` Enter, a harmless guard now that the main process swallows a scan's keys.
- **Form drafts:** the add/edit product form saves itself like the checkout order: every change (debounced) is written to the `settings` table under `product.draft.new` (adding) or `product.draft.<product id>` (editing), via `window.micropos.products.*Draft` and `ProductDraftService`. Closing the dialog (the button reads Close, not Cancel), going to another page to make a category, or restarting keeps it; opening the form again restores it with a "Draft restored" banner (categories deleted meanwhile are dropped). Saving or deleting clears it; **Reset** (shown once something changed) puts the fields back and drops it. A form equal to its starting values has no draft. The page reads the draft before opening the dialog and passes it in the dialog context.
- Gotcha: a dialog opened through `HlmDialogService` must pass its own `id`. Its auto id (`brn-dialog-N`) can equal the id of an `<hlm-alert-dialog>` or `<hlm-dialog>` inside it, which throws "Dialog with ID ... already exists" and the inner dialog silently never opens.

## Categories page

- `pages/categories/` follows the Table design rules (select column, sortable titles, name and created-date filters, default newest first, Reset filters, "Deleted only" switch, row fades). Columns: Name, Products (live products in it, a link to Products filtered to that category via `?category=`), Order (`sort_order`, lower first where categories are listed in order) and Created.
- Add / edit in a dialog (`CategoryForm`, opened with its own dialog id `category-form`); Delete there, in the row menu, by swipe or in bulk always asks first. Delete is a soft delete: the product links stay, so a restore brings the category back with its products. Restore skips a category whose name a live one now uses and names it in a banner. Names are unique ignoring case (`queries/categories.ts`).
- Changes refresh `CatalogService` too, which feeds the checkout filter and the product form's category list.

## Inventory (batches and expiry)

- `products.tracking`: `none` (stock not tracked), `quantity` (one unnamed batch), `batch` (lot numbers) or `expiry` (lot numbers and expiry dates, plus an optional `shelf_life_days` that pre-fills the date when stock arrives). Set it in the product form ("Track stock").
- Stock lives in `product_batches` (one per delivery; unique per product and lot) and the append-only `stock_movements` ledger (`receive`, `sale`, `refund`, `void`, `adjust`, `waste`, `expired`, `repack_out`, `repack_in`; a CHECK ties each type to its sign). **Quantity on hand is never stored: it is the sum of a batch's movements**, so history is complete and refunds simply add stock back. Changing stock means inserting a movement (`receiveStock`, `adjustStock`, `allocateSale`, `restockSale` in `electron/db/queries/inventory.ts`), never editing a number.
- **Repackage** (opening a pack: a sack into loose kilos, a sack into smaller bags; `repackageStock` in `queries/inventory.ts`, `inventory.repackage` over IPC, `RepackageForm`): takes a quantity of a source product out of its batches (first-expiring-first-out, never expired ones) as `repack_out` movements and adds each target as `repack_in` movements, all sharing a `repackage_id`. Each side is typed in its own unit, so a loss is just a smaller target quantity; no pack size is stored on products. Target batches keep the source batch's lot number and expiry (a source without a lot gets `REPACK-yyyymmdd`; a source with no expiry needs one typed when the target expires), and the cost of what was taken is split over the targets by retail value (quantity x price). The whole thing is one transaction. Offered from Inventory (header button, batch menu) and the Products row menu. It is not waste: waste and expiry reports ignore `repack_*`. The form is draftable: one draft in `settings` under `repackage.draft` (`queries/repackage-draft.ts`, `InventoryService.*RepackageDraft`), restored on opening (it wins over the product the dialog was opened from), Reset drops it, saving clears it.
- Selling (`allocateSale`) takes stock first-expiring-first-out (no-expiry batches last, then oldest received), never from an expired batch, and returns the average cost of what it used to store in `order_lines.unit_cost` (margins stay right after costs change). A sale line's movements show which batches it drew from (recalls). **Checkout's Complete sale is not built yet, so nothing calls `allocateSale` outside tests and the seed data**; wire it (and `restockSale` for refunds and voids) when sales are recorded.
- UI: the Inventory page (`pages/inventory/`, under Items) lists batches as a table per the Table design rules (status: Expired / Expiring soon / OK / No expiry / Empty, "Show empty" switch, write-off by bulk button, row menu or swipe with a confirmation). Receive stock (header button, or the Products row menu; a scan picks the product) and Adjust stock (click a row: waste, expired, or a count correction) are dialogs. Products shows a Stock column (quantity, Out, Expiring/Expired) with a stock filter. `EXPIRY_WARN_DAYS` (3) in `@micropos/core` sets "expiring soon".
- The stock overview lives on the Dashboard (`inventoryOverview` in `queries/inventory.ts`, fed into `dashboard()`): stock value at cost and retail, expired and expiring-soon batches with their cost, out-of-stock products, waste written off in 30 days, a Needs attention list and recent ledger activity. Its alert tiles link to the filtered lists (`/items/inventory?status=expired|soon`, `/items/products?stock=out`; both pages read those query params once on open). There is no separate Items > Overview page any more.
- **Edit product from Receive stock:** the product list there includes products that track no stock (marked Not tracked); picking one shows "Stock is not tracked" with Receive disabled. Once a product is chosen an **Edit product** button opens its form over the dialog (with its saved draft), so tracking can be raised to batch or expiry and the lot and expiry fields appear without visiting Products. A scan for a product that does not track stock picks it the same way.
- **Receive another:** a checkbox in the Receive stock footer keeps the dialog open and clears the form after each receipt (a banner names the product received, the Cancel button becomes Close), so products can be scanned and received one after another. The choice is not remembered between openings.
- Expiry dates are entered as dates and stored as the end of that local day (good through the printed date). Packs that print only a month (EXP 11/2026) are entered with the Date / Month toggle in Receive stock; a month is stored as the last day of that month. No precision is kept, so such a batch shows as that last day.

## Completing an order

- *Complete Order* calls `checkout.completeOrder` (`electron/db/queries/orders.ts`): one transaction that writes the `orders` row (numbered SO-1001, SO-1002, ...), its `order_lines`, the `payments` row (cash records tendered and change) and the `sale` stock movements (FEFO, never expired batches, line cost from the batches used), then deletes the `checkout.draft` row. Any failure rolls it all back (`Rollback` sentinel, as in Repackage).
- Payment methods are `cash`, `card`, `ewallet`, `bank_transfer` and `other` (`ORDER_PAYMENT_METHODS` in core, `PAYMENT_METHODS` in the schema; a test keeps them equal, and `payments.method` is plain text so a new method needs no migration). Only cash takes money handed over and gives change; card, e-wallet and bank transfer take an optional reference number, and a refund reverses the payment with the same method.
- The renderer sends only product ids, quantities, the price it showed, the discount and the payment. Names and prices stored on the order come from the catalog. A product that is gone or inactive, a changed price or short stock refuses the whole order with per-line problems; the page then refreshes changed prices, drops unavailable items and keeps the rest so the cashier looks again. Products with tracking `none` have no stock check. Stock cannot go below zero.
- Sales, payments and stock movements are attributed to the signed-in user (see "Users and permissions"). Only where nobody is signed in (the seeder, tests) is the old fallback used: the first active employee, or a "Register" employee created on first use (its PIN hash is invalid, so nobody can sign in as it, and it is left out of the Users page).
- Not built yet: partial refunds, customer prepayments and balance adjustments (the `adjustment` ledger type exists but nothing writes it).

## Sales Orders

- The page (`pages/orders/`) lists every recorded order, newest first, built like the other tables (sortable titles, a filter under each: order number, date range, cashier, payment, status). It has the same selection column and gestures as the other tables; the bulk buttons are **Void N** and **Refund N** (counting only the selected completed sales). A row opens the order; right-click offers View. Void and refund are not built.
- **Void and refund** (`voidOrder` / `refundOrder` in `electron/db/queries/orders.ts`, `OrderActions` in `core/order-actions.ts`, `OrderActionForm`): only a completed sale (`canReverseOrder` in core: status completed and not itself a refund order) can be reversed, once, and always through a confirmation that lists the orders, shows the refund total and requires a **Reason** (up to 200 characters, kept in the audit log with who did it; this tiny form has no draft). Both run in one transaction and put the stock back into the batches it came from (`restockSale` writes `void` / `refund` movements; a sale whose stock was already returned is never returned twice; products that do not track stock have none). A **void** keeps the order, marks it `voided` and leaves its payments as history. A **refund** records a new completed order with negative lines, subtotal, total and payments (same methods, linked by `refundOrderId`/`refundOfOrderId`), numbered from the same SO- sequence, and marks the sale `refunded`; the whole order is refunded (no partial refunds). Refund orders show a **Refund** badge (and their own status filter), and the order dialog links the sale and its refund ("Refund of" / "Refunded by"). Entry points: the order dialog footer (Void, Refund), the table's bulk buttons and the row context menu (which acts on the whole selection when the row is part of it). The acting employee is the first active one until sign-in exists (see Completing an order).
- **Every record dialog opened by a `?view-*` link carries the same page link** (`app-dialog-page-link`, `core/ui/dialog-page-link.ts`): a small ghost icon button (external-link icon, "Open Customers") right after the dialog title (never beside the X, where a press could hit the wrong button), shown only when the dialog is over some other page. It opens the record's page with `?highlight=<id>` and, since that drops the dialog's parameters, closes the dialog. The title always names the kind of dialog ("Sales Order", "Customer", "Product", "Purchase Order") with the record (number or name, status badges) on a line under it: put `<app-dialog-page-link path label [highlight]>` in the title row. Used by the sales order, product, customer account and purchase dialogs; any new record dialog gets one.
- **A `ParamDialogViewer` does nothing while nobody is signed in** (and until a new user has chosen their own PIN): the main process would refuse the load ("Not allowed", logged as a warning), which used to happen at every launch when the last page (`LastRoute`) had a dialog in its address. The address keeps naming the record, and the dialog opens as soon as someone has signed in (`unlocked` in `core/param-dialog-viewer.ts`). Specs that use a viewer need someone signed in: wrap the fake bridge with `withSession(api)` from `core/auth/testing.ts`.
- **`?view-sales-order=<order id>`** on any page opens that order in a dialog (`SalesOrderForm`, view mode) over the current page. `SalesOrderViewer` (`core/sales-order-viewer.ts`, started by `App`) watches the address, loads the order (`orders.get`) and opens or closes the dialog to match; closing removes the parameter (replacing the history entry, so Back does not reopen it); an unknown id shows an "Order not found" banner and clears the parameter. Both this and `?view-product` are `ParamDialogViewer`s (`core/param-dialog-viewer.ts`) and can be open together, each with its own parameter. To link to an order call `viewer.open(id)` or use a `routerLink` with that query parameter. Over any page except `/orders` the dialog footer has an icon-only external-link button (`lucideExternalLink`, "Open Sales Orders") (going there drops the parameter, which closes the dialog). The form takes `mode: 'view'` in its dialog context; add edit modes there when needed.
- **`?edit-product=<product id>`** on the Products page opens that product's edit dialog (`ProductsPage.openById`). The product is looked up by id (`ProductsService.find`), so it opens whatever the table's filters show; the row is flashed and scrolled to when visible. Unlike `view-sales-order`, the parameter is consumed at once (replaced out of the address) because the product form manages its own dialog. A deleted product shows a "was deleted" banner instead (deleted products are read-only). The tables are not paginated; if Products ever is, find the row's page with a count of rows sorting before it (offset paging).
- **`?view-product=<product id>`** on any page opens a read-only product dialog (`ProductView`, `ProductViewer`) over the page, deleted products included; it shows price, PLU or barcode, SKU, how it is sold, cost, stock, next expiry and categories. In the sales order dialog a line's product name opens it (on top of the order, which stays open) and a small link button beside the name goes to the product on the Products page; the product dialog has the same link as an icon button in its footer (not shown while already on Products). The link is `/items/products?highlight=<id>`: the Products page shows the page holding the product, highlights the row, clears filters that hide it and switches to Deleted only for a deleted product. Following it drops every dialog parameter, so all the dialogs close. Lines whose product was removed for good stay plain text.
- **`?new-product=<barcode>`** on any page opens the add-product form (`ProductForm` with a `prefill` context, `NewProductViewer`, a `ParamDialogViewer`) over the page with that barcode filled in and stock tracked by quantity, so a product can be created where it was found missing without visiting Products. A prefilled form keeps no draft (it would clobber the Products page's own add-form draft). Receive stock uses it: a scan for a code no product has shows "Create product"; once the product is saved the form picks it (a code that belongs to a product that does not track stock says so instead). Link to it with `NewProductViewer.open(code)`.
- Banners can carry an action button (`banner.success(text, { action: { label, run } })`); it sits right beside the message (the pair is centered), and pressing it runs the action and dismisses the banner. Checkout uses it for **View** after Complete Order (6 s instead of the usual long duration, so there is time to press it).

## Customers and credit (store credit, partial payments)

- A **customer** (`customers`: name, phone, note, optional credit limit; soft delete) can buy on account. What they owe is the sum of their **ledger** (`customer_ledger`, append-only like the stock ledger, never edited): `charge` (the unpaid part of a sale, positive), `payment` (money received, negative), `refund` and `void` (cancelling the charge of a credit sale, negative) and `adjustment` (either way, reserved; nothing writes it yet) and `interest` (positive; see Credit interest). A CHECK keeps each type's sign right. Positive balance = the customer owes the store; negative = the store owes them (a refund after they had paid off the debt). There are no per-order allocations: payments go to the account, not to a particular sale.
- **Credit sale** (`completeOrder`): `customerId` plus `amountPaid` (cents paid now, 0 to the total; omitted = the whole total). The payment row holds only what was paid (none when 0; cash `tendered` only has to cover `amountPaid`, and change is worked out from it), `orders.customer_id` links the sale (also when it was paid in full) and a `charge` entry puts `total - amountPaid` on the account. Without a customer the whole total must be paid. A customer's credit limit is enforced inside the transaction (balance + charge may not pass it); a deleted customer cannot be used. Checkout shows a **Customer** combobox and, once one is chosen, **Pay now** (default the whole total) with the amount **On account**, the customer's balance and limit, and refuses a charge over the limit; with Pay now at 0 (the whole sale on account) the payment method, reference and cash fields are hidden, since there is no payment; the customer is cleared after each sale.
- **Receive payment** (`receivePayment`, the customer account dialog): amount (never more than they owe; a bigger amount is almost always a typo, and prepayments are not supported), method (`ORDER_PAYMENT_METHODS`) and an optional reference; it writes a `payment` entry by the acting employee (see Completing an order).
- **Void and refund** a credit sale cancel what it left on account (`void` / `refund` ledger entry for the charged amount; a refund's entry is attached to the refund order, whose `customer_id` is the same). The paid part is returned as before (negative payments).
- **Customers page** (`pages/customers/`, route `/customers`, nav rail "Customers"): the standard table (selection gestures, paging, highlight, `?highlight=<id>`) with Name, Phone, Owes (red; "Credit" when negative), Limit and Last activity, a balance filter (Owes, Settled, Has credit), add/edit/delete (a customer with a balance cannot be deleted; the bulk Delete counts only those without one) and Deleted only/Restore. A row opens the **account dialog** (`CustomerAccountForm`, `?view-customer=<id>` via `CustomerViewer`, a `ParamDialogViewer`): balance, limit, phone, note, a **Receive payment** form (amount with a Full balance shortcut, method, reference), Edit, and the ledger newest first, each entry with what was owed right after it and sale numbers that open the order over the dialog. Sales Orders has a **Customer** column (with what went on account) and filter, and the order dialog shows the customer (opens their account) and the On account amount.
- **Credit interest** (optional, per customer; most customers have none). Pure rules in `packages/core/src/credit-interest.ts`, accrual in `electron/db/queries/credit-interest.ts` (`accrueInterest`). `customers.interest_mode` is `order` (**per sales order**: each credit sale is charged on its own unpaid amount, first 15 days after the sale, then monthly; never on earlier interest) or `total` (**on total credit**: monthly from when interest was switched on, on everything owed at that moment, interest included, so it compounds); `interest_rate_bp` is the monthly rate in basis points (300 = 3%); `interest_started_at` is when it was switched on (only sales charged after it earn interest; changing the kind restarts it, changing only the rate does not). Interest is a ledger entry of type `interest` (positive, `order_id` set for per-order interest, no employee), dated when the period fell due. Payments carry no per-sale allocation, so for per-order interest they are applied **oldest sale first** when working out what each sale still owes (`unpaidByOrder`); a refund or void stops interest on that sale (interest already charged stays on the account). A period is done once an entry dated exactly at its due time exists, so `accrueInterest` is idempotent: `main.ts` runs it at startup (catching up months missed while closed) and then hourly. A month with nothing owed (total) or an interest of under half a cent writes nothing.
- **Interest defaults** (what a customer's rate starts from when interest is switched on for them; each customer keeps their own copy and later changes do not touch existing customers): two monthly rates (`orderRateBp`, `totalRateBp`, factory 3% each) in the `settings` table under `customerInterestDefaults` (`getInterestDefaults` / `saveInterestDefaults`, IPC `customers.interestDefaults` / `saveInterestDefaults`). Edited in Settings > Credit Interest (`pages/credit-interest-settings.ts`); the customer form's **Interest on credit** select (No interest, Per sales order, On total credit) fills the rate from them. The account dialog shows the customer's interest and its entries in the ledger. Permission: all of this needs `customers.manage` (the IPC calls are guarded and the Settings card is hidden without it).
- **Nav rail badges and credit alerts:** a nav entry may carry `badge: '<id>'` (`NavItem` in `core/nav-rail.ts`); `NavBadges` (`core/nav-badges.ts`) holds the counts by id and draws a small red number on the entry's icon (a group shows its children's total; 0 shows nothing; 99+ is capped). It refreshes on sign-in and whenever the main process announces a change (see **Live updates**), with a 30-minute safety net; it also holds the concern lists (`stockConcerns`, `purchaseConcerns`) that the concerns dialogs read, so an open dialog follows every refresh. To add a badge: read its count in `NavBadges.refresh()` under the entry's id, guarded by the permission of the page it points at, **and give that page the same follow-up as Customers**: an `app-concerns-button` (`core/ui/concerns-button.ts`) beside its title showing the same number, opening a "… concerns" dialog that lists them with their reasons and filters, a row going to the record. A badge never ships without it. The only one so far is **Customers**: the number of customers who need attention (`customers.alertCount`, `countCreditAlerts` in `electron/db/queries/credit-alerts.ts`, rule `creditAlert` in core): someone who **owes more than the alert amount**, or whose **oldest unpaid sale is older than the alert days** (payments are applied oldest sale first, as for interest). Each customer counts once. The Customers page shows the same flag: `CustomerRecord.alert` (`{ overAmount, unpaidDays }`, filled in by `listCustomers` from the same `creditAlerts` rule) feeds a warning-coloured **button beside the page title** whose label is the number of concerns (hidden at 0); it opens the **Credit concerns** dialog (`CreditConcerns`), the flagged customers largest balance first, each with its reason ("Over ₱5,000.00 · Unpaid 45 days", `alert-text.ts`) and balance, a row opening the customer's account; the dialog has a name filter and a reason filter (All reasons, Over amount, Unpaid too long). There is no filter or per-row marker for it: the button is the one place. The two limits are shop-wide (`settings` table, key `creditAlerts`, factory ₱5,000.00 and 30 days) and are edited in Settings > Credit Alerts (blank = that limit is off; both off = no badge). Permissions: the count needs `customers.view` (the same as the Customers link); reading and saving the limits needs `customers.manage` (the Settings card is hidden without it).
- **Live updates (`data:changed`):** the main process tells every window which parts of the data changed (`DATA_DOMAINS` in core: `customers`, `stock`, `purchases`; renderer `api.data.onChanged`). Two sources: (1) **writes**: `guarded()` in `electron/ipc/index.ts` announces after a write channel succeeds (not when it returns `{ ok: false }`), using the table in `electron/ipc/changes.ts` (`WRITES`: channel to the parts it changes; `UNRELATED`: every other channel). A test fails for a channel in neither, so **a new IPC channel must be classified there**. (2) **Time**: `electron/concerns-clock.ts` computes the next moment something becomes a concern without a write (a batch entering its expiry window or expiring, an order falling late or overdue, a customer's oldest unpaid sale passing the days limit; `nextConcernAt`, built from `purchaseConcernDueAt` / `creditAlertDueAt` in core) and sleeps until then (at most 6 hours, recomputed after every announcement, and again when the computer wakes), then announces everything. Hourly interest accrual announces `customers` when it charged something. Listeners: `NavBadges` (refresh, coalescing announcements within 100 ms) and the data services (`CustomersService`, `InventoryService`, `PurchasesService`, `ProductsService` reload their list through `refreshOnChange`, once loaded), so pages and dialogs stay current without each writer remembering to refresh. A new part of the data that badges depend on: add it to `DATA_DOMAINS`, classify the channels, and listen where needed.
- **Stock and purchase concerns** (badges on Items > Inventory and Purchasing > Purchases, each with the page's `app-concerns-button` and dialog). Lists come from the main process, rules in `packages/core/src/concerns.ts`: `stockConcerns` (`electron/db/queries/inventory.ts`) returns `StockConcern[]`, worst first: **expired** batches and **expiring soon** batches (within `EXPIRY_WARN_DAYS`, 3) that still hold stock, products **out of stock**, and products **low** (on hand at or below their critical level); only live, active products that track stock. `purchaseConcerns` (`queries/purchases.ts`, rule `purchaseConcern` in core) returns orders **late** (still to arrive, expected date passed) or with **payment overdue** (owed and past the due date), the longest overdue first. IPC `inventory.concerns` (needs `inventory.manage`) and `purchases.concerns` (`purchasing.manage`); the badge is the list's length, and the page button reads the same number from `NavBadges`. Dialogs: **Stock concerns** (`pages/inventory/stock-concerns.ts`; filters product and kind; a row opens the product) and **Purchase concerns** (`pages/purchases/purchase-concerns.ts`; filters order/supplier and reason; a row opens the order). A sub-entry in the nav rail (no icon) shows its number at the end of its row, and its group shows the total on its icon.
- **Critical level** (`products.critical_level_milli`, thousandths of the unit, null for none; the form's **Critical level** field, shown for products that track stock; kept in the product form draft as `criticalLevel` text). Stock at or below it makes the product a "low stock" concern; nothing is checked for products whose stock is not tracked. The seeder gives most tracked products one.
- Seed data (`customer.factory.ts`, `seed.ts`): six customers; about 15% of completed sales are credit sales (part paid, the rest charged within the limit), followed by some payments, so the pages have balances to show. The ERD (`docs/erd.mmd`) has `customers`, `customer_ledger` and `orders.customer_id`.

## Purchasing (suppliers, purchase orders, paying later)

- A **supplier** (`suppliers`: name, phone, note; soft delete) is who the store buys from. A **purchase order** (`purchase_orders`, numbered PO-1001, ...; `purchase_order_lines`: product, quantity, unit cost; `purchase_payments`) records stock ordered in advance and paid later or in parts. Status: `ordered` (placed, not here), `received`, `cancelled`. Optional expected delivery date, payment due date and the supplier's own reference. **What is owed = total - sum of payments** (0 for a cancelled order); supplier balance is the sum over their orders. No ledger: payments are tied to the order they pay.
- `electron/db/queries/purchases.ts`: `createPurchase` / `updatePurchase` (only while `ordered`; lines are replaced, a product appears once, the total may not drop below what is paid), `payPurchase` (deposit allowed before arrival; never more than owed; `purchase_payments` is append-only, amount CHECK > 0), `cancelPurchase` (only `ordered` with nothing paid), `receivePurchase`.
- **Returning stock to a supplier** (expired bread, a damaged delivery; Items > Inventory, a batch's menu > **Return to supplier**, `ReturnToSupplierForm`; IPC `inventory.returnToSupplier`, needs `purchasing.manage`; `returnToSupplier` in `electron/db/queries/supplier-returns.ts`): the batch loses the quantity (a `supplier_return` stock movement), a `supplier_returns` row records it (supplier, the order the batch came on, quantity, refund, `credited_amount`, note, who). The order and supplier come from how the batch was received (`BatchRecord.purchaseNumber` / `supplierName`; stock received by hand has none, so the form asks for a supplier). The **refund is optional and may be partial** (never more than the cost of what goes back, when the cost is known); it **first reduces what is still owed** on that order (`credited`, so `owed = total - paid - credited`, also in the supplier's balance), and any excess is just recorded: there is no cash register to reconcile, so no refund method or reference. The order dialog shows a Refunded line and the Returns list; returns also appear in the dashboard's recent movements ("Returned to supplier"). A returned expired batch stops being a stock concern. The IPC announces `stock` and `purchases` changes.
- **Receiving a delivery** (`receivePurchase`, the order dialog's Receive stock = a **receiving session**, `PurchaseReceiveForm`): each line shows what is left; scan a product (counts one as arrived) or type the quantity, or **Everything left**; lot and expiry appear for a line once something arrives. Receive first checks the entries (quantities, lot, expiry) and then asks for confirmation, listing what goes into stock (or saying nothing will, for an order of products that track no stock); nothing is written until it is confirmed. Only what arrived is received (short deliveries leave the order **Partly received**; leaving a line out of the call takes all that is left of it), in one transaction: each line of a stock-tracked product goes in through `receiveStock` (given the outer transaction) as a `receive` movement at the ordered cost with the note "Received on PO-n"; lot number and expiry are needed for products that track them (`ReceiveLineInput`); products with tracking `none` are only recorded as bought. If any line is refused nothing is received. After receiving, the order can still be paid.
- UI: **Purchasing** group in the nav rail with **Purchases** (`pages/purchases/`: table with order/reference, supplier, date range, status and owed filters, overdue due dates in red, total owed in the header, no selection or bulk actions since orders are cancelled, not deleted) and **Suppliers** (`pages/suppliers/`, the standard table with delete/restore; a supplier owed money or with an order on the way cannot be deleted; "View purchases" opens Purchases filtered by `?supplier=<id>`). `?view-purchase=<id>` (`PurchaseViewer`) opens the order dialog (`PurchaseDetailForm`: lines, totals, record payment, edit, receive stock, cancel order) over any page. The new/edit order form (`PurchaseForm`) and the receive dialog (`PurchaseReceiveForm`) are not draftable yet.
- Seed data (`purchase.factory.ts`): four suppliers and ten orders (mostly received into the product's existing unnamed batch so stock stays consistent, some on the way, a few cancelled; paid in full, in part or not at all). The ERD has the four new tables.
- **Receive stock against an order, in parts:** `stock_movements.purchase_order_line_id` ties a receipt to the order line it was delivered against; **what has arrived of a line is the sum of those receipts** (`receivedMilli`). Receive stock (opened from the Inventory page, or from an order's dialog by **Receive by item**, which goes to `/items/inventory?receive-order=<id>` where the dialog opens with that order chosen (the parameter is then removed); the Purchases page header has no Receive stock button) has an optional **Purchase order** field (orders still waiting for stock): choosing one lists its own products with something still to come (products that track no stock included, marked Not tracked), with a note saying so ("Showing only products on PO-n"; clear the order to receive anything else), shows "Ordered n · received n · n left", and starts quantity and cost at what is left and the ordered cost (a scan of a product not on it is refused). `receiveStock` refuses a line that is not that product's, an order already received or cancelled, and more than is left. When everything ordered of the stock-tracked products has arrived the order becomes received by itself (`settlePurchase` in `queries/purchase-receipt.ts`; products that track no stock never hold it back). Until then it shows as **Partly received**; such an order cannot be edited or cancelled (its lines carry receipts), and "Receive the rest" in its dialog takes only what is left. Receive another keeps the order chosen for the next product.
- Not built yet: refunds from a supplier, cancelling an order with money paid on it, per-supplier statements.

## Users and permissions
- **Accounts are the `employees` table** (`employeeNumber`, scrypt `pinHash`, `role`, `permissions`, `pinChangeRequired`, `active`, lockout columns). Sign-in is a **PIN pad**: the lock screen lists the active people by name (tiles), then asks for the PIN (4 to 8 digits, `isValidPin` in core). Five wrong PINs in a row pause that person's sign-in for a minute (`MAX_FAILED_SIGN_INS`, `SIGN_IN_PAUSE_MS`).
- **Permissions are per-user switches** (`PERMISSIONS` in `packages/core/src/auth.ts`: checkout.sell, orders.view, orders.reverse, customers.view/manage/payments, catalog.view/manage, inventory.manage, dashboard.view, discounts.give, reports.view, purchasing.manage, settings.manage, users.manage). `role` (admin, manager, cashier) is only the preset a user started from (`ROLE_PRESETS`); what counts is `permissions` (null, on rows from before permissions existed, means the role's preset). The Users page shows "Custom" when the switches match no preset. To add a permission: add it to `PERMISSIONS` (and presets), gate the IPC channels that need it (`ipc/index.ts`), the route (`requires()` in `app.routes.ts`) and the nav entry (`permission` in `nav-rail.ts`).
- **The main process is the gate.** `electron/auth/auth.ts` holds the one session (module-level: one person at a time), and every IPC handler except `app:version`, scanner, display and the sign-in calls goes through `guarded(db, channel, permission(s), handler)` in `ipc/index.ts`; a call without the permission rejects with "Not allowed". A list means any one of them (e.g. suppliers and purchases can be read by anyone who manages stock, so Receive by purchase order works). The session is re-read from the database on every call, so a permission change or deactivation applies at once. The pages only hide what is not allowed: `AuthService.can()`, route guard `permissionGuard`/`requires()`, nav entries.
- **Lock screen:** `SignInScreen` covers everything (dialogs included, z-index above the overlays) while nobody is signed in, and the router outlet is not rendered then. Nav rail: the signed-in name and a **Lock** button (closes open dialogs, ends the session). After signing in, `AuthService.signIn` checks the page the router is on and moves to the first allowed page (`PAGE_PERMISSIONS`) if it is not theirs. The session survives a window reload (the main process keeps it) and ends when the app quits.
- **Admin-only settings:** `settings.manage` ("Change shop settings", admin preset only, like `users.manage`) is for settings that affect the whole till rather than one person; Settings cards for them are hidden without it and their IPC calls are guarded by it. Migration `0008` gave it to everyone whose permission list already held `users.manage`.
- **Keep running in the tray** (Settings > Window, `settings.manage`): `shell.getCloseToTray` / `setCloseToTray` (`electron/close-to-tray.ts`, stored in the `settings` table as `closeToTray`, off by default). When on, closing the main window only hides it (`win.on('close')` in `main.ts` prevents the close) and a tray icon (`electron/tray.ts`: click or Open brings the window back, Quit really quits) keeps the app running for background work and, later, notifications; turning it off removes the icon and shows the window if it was hidden. The tray is the notification area beside the taskbar clock: a hidden window has no taskbar button. `quitting` (set on `before-quit`) lets Quit, the system shutting down and the installer close it for real; **when an auto-updater is added, also set it on `autoUpdater`'s `before-quit-for-update`** (it closes windows first, which would otherwise be blocked). Only one MicroPOS runs at a time (`requestSingleInstanceLock`): starting it again while it is hidden brings the till back. The till is not locked when hidden: whoever reopens it finds the signed-in user (use Lock first if that matters).
- **Starting PINs:** a fresh database gets an admin "Owner" (`ensureOwner`, called at startup; employee number 1001, or the next free one) with PIN **1234** and `pinChangeRequired`, so the first sign-in must choose a PIN of its own (the lock screen shows the change form until then). Users created or reset by an admin also have `pinChangeRequired`. `ensureOwner` does nothing while someone who can sign in holds `users.manage` (so the seeded dev admin, `1001` / `1234`, is used as is). A user can change their own PIN in Settings > Account.
- **Users page** (`/users`, needs users.manage): add and edit users (name, employee number, starting PIN when adding, preset then switches, "Can sign in"), reset a PIN, and the latest 2000 sign-ins (`login_sessions`), paged 50 at a time like the other tables (sign-out is recorded on Lock and at quit, an open row from a crash shows "-"). Users are never deleted (their history points at them); a user is deactivated. The last person able to manage users cannot lose that, and nobody can deactivate themselves. User changes are written to `audit_log` (`user.create`, `user.update`, `user.pin-reset`, `user.pin-change`).
- **Who did it:** `electron/auth/actor.ts` holds the signed-in employee id; `sellingEmployee()` and the stock functions' `employeeId` default read it, so orders, voids/refunds, ledger entries, purchase payments and stock movements carry the user without every call passing it.
- Specs that fake `DesktopApi` need `auth` and `users` members; `core/auth/testing.ts` has `fakeAuthApi` and `sessionUser` for tests that need someone signed in (without a main process, `AuthService` treats everyone as allowed so pages and tests that do not care keep working).

## Printing and logging

- **The main process owns the printer** (it is the local business server: the till's window prints through it now, phones over the local network will later). **The receipt header:** the logo when the shop has one, then below it the **shop name as plain bold text** (wrapped when long) and the address, all centred; without a logo it starts at the name. Receipts are built in **pure code in core** (`packages/core/src/receipt.ts`: `buildSaleReceipt`, `buildTestReceipt` make a `ReceiptDocument` of text, column, rule, feed and logo lines for N characters per line; `columnsFor` / `dotsFor` give 32 characters and 384 dots for 58 mm paper, 48 and 576 for 80 mm; amounts print without a symbol and the total as `PHP`, since printer code pages have no peso sign). Nothing in the page builds or encodes a receipt. Everything printer-specific is in `electron/printing/`.
- **Pipeline:** `PrinterService` (`printer-service.ts`) takes a document, reads the saved settings for that job, encodes it (`escpos.ts`, the `@point-of-sale/receipt-printer-encoder` package), and sends it through a `PrinterTransport` (`transports/types.ts`: one `send(bytes)` = one job that connects, writes and lets go, so every job starts from the same state and there is no connection to keep alive or reconnect). Jobs run one at a time in arrival order; `print` / `printSale` / `printTest` never throw and return a `PrintResult` (`ok`, or a `PrinterErrorCode` plus text: `not-configured`, `unreachable`, `timeout`, `no-printer-interface`, `busy`, `write-failed`, `unsupported`, `unknown`); a transient failure (`timeout`, `busy`, `write-failed`) is retried once. Errors are typed (`PrinterError`), never matched by their text. A remote client later calls the same service.
- **Transports:** `NetworkTransport` (raw ESC/POS on TCP, port 9100; the job is done when the bytes are flushed, since printers often keep their side open) and `UsbTransport` (the `usb` package, loaded only when used so a machine where it cannot load still runs; finds the printer-class interface and its bulk-out endpoint, sends in packet-sized chunks, always releases and closes). **Windows caveat:** claiming a USB interface only works when the printer uses the WinUSB driver (not Windows' own printer driver); not tried on real hardware. Network printers avoid that.
- **Every job states its setup** instead of trusting the printer's leftover state: full reset (ESC @), left margin 0 (GS L), print width = the paper's dots (GS W), align left. A logo is centred **inside its own bitmap** (`bitmap.ts` `centerOnPaper`: a white strip as wide as the paper, transparency made white), so it cannot come out off-centre whatever alignment a freshly switched-on printer is in (the old app's first print after boot was off-centre; cause was never confirmed). **The logo** is uploaded in Settings > Receipt Printer (Upload / Replace / Remove, PNG or JPEG up to 5 MB, with a preview on white): `printer.saveLogo` sends the file's bytes, `LogoStore` (`printing/logo-store.ts`) checks them, scales them to at most 576 dots wide (the widest paper) and stores a PNG as `receipt-logo.png` in the user data folder (written beside the real file and renamed into place, so a failed upload keeps the old logo); `loadShopLogo` (`logo.ts`) **trims the blank border** (transparent or near-white edges, `contentBounds` in `bitmap.ts`: a logo exported with spare space would otherwise push the shop name far below it; the stored file is left as uploaded), scales it for the paper in use, centres it and leaves a 12-dot gap under it (`LOGO_GAP_DOTS`) before the shop name. The debug image uses the same trimmed picture and gap (`trimmedLogoPng`).
- **Settings** (`printer.settings` / `save` / `getLogo` / `saveLogo` / `removeLogo` / `listUsb` / `testPrint`, `settings.manage` = admins; stored in the `settings` table as `printerSettings`, validated in `printing/settings.ts`): connection (none, network host and port, or a USB printer chosen from the list), paper width (58 or 80 mm), shop name, address and closing message. Settings > Receipt Printer (`pages/printer-settings.ts`); Test print saves, then prints a ruler page. Printing a sale is `printer.printOrder` (`orders.view` or `checkout.sell`): the **Print receipt** button of the order dialog. Auto-printing after a sale is not built.
- **Printing a sale** (`ReceiptPrinting`, `core/receipt-printing.ts`: one place that asks for it and words the outcome): the **Print receipt** button of the order dialog, **Print receipt** in a Sales Orders row's menu, and Checkout's **Print receipt** switch (`AppSettings.printReceiptAfterSale`, per device, remembered): with it on, the receipt is requested once the sale is recorded and the result is added to the same sale banner ("... · receipt printed", or a warning "... · receipt not printed: <reason>"; the sale stands either way).
- **The order QR code** (the last thing on a sale receipt, `buildSaleReceipt`): a QR of `MICROPOS-ORDER-<order number>` (`orderQrPayload` / `parseOrderQr`, core `order-qr.ts`: letters, digits and dashes only, so a keyboard-wedge scanner types it right on any keyboard layout). It is built from the QR's own modules (`printing/qr.ts`, the `qrcode-generator` package, error correction M, quiet zone of 4 modules, modules 2 to 8 dots so it fills up to 60% of the paper) and **sent to the printer as a picture centred inside its own strip** (like the logo), so it prints the same on any printer, whether or not it has a QR command, and the debug image draws it from the same modules. Tests decode the printed bitmap back with `jsqr` on both paper widths. **Scanning it opens the sale:** `OrderQrScan` (`core/order-qr-scan.ts`, started at the root) is a scanner **hook** (`ScannerService.addHook`: sees every scan before the claims, after a focused scan input; returning true takes the scan), recognises the code, asks `orders.idByNumber` (needs `orders.view` or `customers.view`) and opens `?view-sales-order=<id>` over whatever page is showing; wherever the scanner is claimed (Checkout, a form), the receipt code is never taken for a product. Someone without `orders.view` only gets a note ("You cannot open sales orders"); an unknown number says "Order <n> not found". Any other code is left to the pages as before.
- **Debug: receipts as images** (Settings > Debug, `settings.manage`; `debug.get` / `setSaveImages` / `openReceiptsFolder`; stored as `printerDebugSaveImages`): while on, every receipt (sales and the test page) is saved as a PNG in `Downloads/MicroPOS receipts/` (`receipt-<order>-<yyyymmdd-hhmmss>.png`, never overwritten) **instead of being sent to the printer, and no printer needs to be set up**; the result is `{ ok: true, savedTo }` and the banners say so. This is the way to check layouts without hardware. Built in two steps: `layoutReceipt` (core, pure: the document as the exact characters on each row of paper, tested) and a rasterizer (`receipt-image-electron.ts`: a hidden window draws each character in its 12 x 24 dot cell, the logo scaled and reduced to black and white). The image shows the layout and the logo; it is **not** a capture of the printer's own bytes (ESC/POS commands, codepages and the printer's rendering are not shown), so the real centring of a logo and any first-print behaviour still need a real printer. `ReceiptImageSink` (`receipt-image.ts`) is the stand-in `PrinterService` uses (`images` dependency) while the setting is on.
- **No printer was available when this was written:** the document layout, the ESC/POS bytes, centring, the network transport (against a real local socket), the USB transport (against a fake device), the service (queue, retry) and the settings are covered by tests (`printing/printing.spec.ts`); printing on real hardware, and the USB path on Windows, are **unverified**.
- **Logging** (`electron/logging/`): plain text files, one per day, `micropos-YYYY-MM-DD.log` (a day's file that reaches 5 MB continues in `-1`, `-2`...; 14 days are kept, older ones deleted at startup; nothing else in the folder is touched). One entry per line, `ISO-time LEVEL [source] message`, with a stack or details indented under it. Folder: the system's log folder when installed (`app.getPath('logs')`, `%APPDATA%\micropos\logs` on Windows), `apps/desktop/local-data/logs` in development. Settings > Logs shows the path and an **Open folder** button (`shell.getLogsFolder` / `openLogsFolder`, `settings.manage`), so an admin can copy or send the files. Use `log.error|warn|info(source, message, details?)` from `electron/logging` (it only prints to the console until `initLogging` runs, and in tests). **Never log secrets:** pass messages and errors, not request data (PINs travel in IPC arguments, which are never logged).
- **What is logged:** every IPC handler that throws (`ipc:<channel>`, with the stack; a refused call is a warning), uncaught exceptions and unhandled rejections in the main process, the window's process ending or hanging, interest accrual failures, printer failures and successes, app start and quit, and **errors in the page**: `ErrorReporter` (Angular's `ErrorHandler`, which also receives window errors and unhandled rejections through `provideBrowserGlobalErrorListeners`) sends them over `log.write`, an open channel (an error can happen before sign-in) bounded to 50 entries a minute and short fields.

## Discounts and sale notes

- **Discounts** (checkout, `discounts.give` "Give discounts": managers and admins, not the cashier preset; migration `0013` gave it to everyone who could void/refund or manage users). Two levels, both an **amount or a percent**, with **no upper limit** other than the price (core `discount.ts`: `DiscountSpec` = `{ mode: 'amount' | 'percent', value }` with cents or basis points, `discountCents(spec, base)` clamps to the base, `parseDiscount` reads the typed text). A **line discount** (right-click or long-press an item > Discount) is stored on the draft line (`DraftLine.discount`, saved with the draft) and comes off that line; the **order discount** (Add/Edit beside Discount in the totals) is a percent of, or an amount off, what is left after the line discounts and keeps following the cart (a percent recomputes as items change). One optional **reason** per order (`orders.discount_reason`, shown in the order dialog, kept on a refund order; dropped when nothing was discounted). Without the permission the controls are not shown, and `checkout.completeOrder` refuses an order that carries any discount (`givesDiscount`, `ipc/discount-gate.ts`).
- **Storage:** `order_lines.discount` (cents off the line; `line_total` stays price x quantity, so Items sold totals are before discounts, as order discounts were never spread over items), `orders.discount_total` = line discounts + order discount (so `total = subtotal - discount_total` still holds and Reports/Dashboard "discounts" include both). Refund orders and refund lines carry the negated amounts. The main process re-checks that a line discount is at most its line and the order discount at most what is left.
- **Notes/remarks:** `orders.note` (at most 200 characters, optional): the "Note on this sale" field at the bottom of the Payment panel, shown in the order dialog and printed at the bottom of the receipt ("Note: ..."). Saved with the draft (with the order discount and its reason; the payment fields are not). Receipts print each line discount under its item.

## Devices (phones and tablets over the network)

`/devices` (nav "Devices", `settings.manage`) turns the till into a server for other devices on the shop's Wi-Fi (off by default; the on/off is stored in `settings` as `lan` and the server starts at launch when it was on). A phone **scans the QR code with its camera**, opens `https://<till ip>:8734/?pair=<code>` and gets **the same Angular app**, which talks to the till instead of Electron. Each person still signs in with their PIN on the phone, with their own permissions.
- **Server** (`electron/lan/`, class `LanServer`, node `https` + `ws`, no other packages): serves the built renderer (`dist/renderer`; in development it proxies `ELECTRON_RENDERER_URL`), marking the page with `window.__MICROPOS_LAN__` (`LAN_MARKER`); `POST /lan/pair {code}` trades a one-time code (`PairingCodes`, in memory, 5 minutes, used once, 10 tries a minute per address) for a device token (a row in `lan_devices`; only the SHA-256 is stored); `POST /lan/rpc {group, method, args}` with `Authorization: Bearer <token>` runs **the very same handler the till's window would** (`rpcHandlers` in `ipc/index.ts`: every `guarded()` / `handle()` registration is also kept in that map), so permission checks, logging and data-change announcements are shared; `/lan/ws` pushes `{type:'changed', domains}` (the same `data:changed` events as windows, via `broadcast` in `main.ts`) and shows who is online. **Not available to a device** (`channelFor` in `server.ts`): groups `shell`, `debug`, `display`, `scanner`, `lan`, and `reports.export` and the printer settings/logo/USB/test channels; a phone may print a receipt (`printer.printOrder`) on the till's printer. A new IPC channel is reachable from devices by default: add it to the denied sets if it touches the till's own hardware, files or windows.
- **One session per device** (`auth/context.ts`): sign-in state and the "actor" for attribution live in a `SessionState`; the till's window uses the default one and a device's calls run inside `runAsSession(state, ...)` (an `AsyncLocalStorage`), so a phone signing in or out never changes the till's session or another phone's. Sessions are in memory: restarting the till signs every phone out (they stay paired). Unpairing (`LanService.revoke`) signs the device out and closes its sockets with code 4001, which sends the phone back to the "not paired" page.
- **HTTPS** with a self-signed ECDSA certificate made with Node's crypto (`lan/certificate.ts`, a minimal X.509 writer; stored in the user data folder as `lan-certificate.json`, reused while it is valid for a month more and names every current address, otherwise remade, which makes phones warn again). Phones warn once ("not private"): the Devices page says to choose Advanced and continue; the traffic is encrypted either way.
- **Renderer**: `DESKTOP_API` is `window.micropos` or, on a device (`isLanDevice()`), `createRemoteApi()` (`core/api/remote-api.ts`): a Proxy that sends every `api.<group>.<method>(...)` to `/lan/rpc` (a refused call rejects with the till's message, like IPC), `data.onChanged` is the shared WebSocket (reconnects and asks everyone to refresh), and the till-only parts (customer display, scanner) answer harmlessly. `main.ts` first pairs from the address (`pairFromAddress`) and shows only "This device is not paired" (`showNotPaired`) when it cannot.
- **First version: load and scroll.** The layouts are the desktop ones (designed for 1024 px): on a phone pages scroll sideways, and Settings cards for the till's own hardware (printer setup, window, logs, debug) fail there. Not done: phone-tuned layouts, a bottom navigation, a per-device checkout draft (the checkout draft is one per till, so a phone and the till share the order in progress), reconnecting sessions after a restart.
- Tests: `lan/certificate.spec.ts` (a real HTTPS server with the certificate), `lan/server.spec.ts` (serving, pairing, per-device sessions, WebSocket pushes, path traversal), `lan/devices.spec.ts`, `pages/devices/devices.spec.ts`, `core/api/remote-api.spec.ts`. The wiring in `ipc/index.ts` / `main.ts` (Electron itself) is not unit tested.

## Dashboard

`/dashboard` (first entry of the nav rail, `dashboard.view`: managers and admins; migration `0011` gave it to everyone who had `catalog.view` or `reports.view`, replacing the old Items > Overview) is read-only: sales today against yesterday, the last 7 and 30 days with the average sale, a bar chart of net sales for the last 14 days, what was taken by each payment method (7 days), best sellers (30 days), what customers owe (and who owes most), what is owed to suppliers (and how much is overdue), and the whole stock overview. `dashboard.get` -> `dashboard()` (`electron/db/queries/dashboard.ts`, types in core `dashboard.ts`); its sales numbers come from `salesReport`, so they match Reports, and the chart is one query by completed day. Each bar of the 14-day chart is a link to `/orders?date=YYYY-MM-DD` (Sales Orders reads `DATE_PARAM`, sets the Date filter to that single day and removes the parameter). It refreshes itself on the `sales`, `stock`, `customers` and `purchases` data changes (`sales` is announced by checkout, void and refund).

## Auto sign-out (session expiry)

Settings > **Auto sign-out** (`settings.manage`, `pages/session-settings.ts`): sign the person out after N minutes without input, N whole minutes from 1 to 1440, blank = never (the default; stored in `settings` as `sessionTimeoutMinutes`, `auth.setSessionTimeout`). **Activity is input on the page** (pointer, key, wheel, touch; `core/auth/activity-monitor.ts`, started by `App`), not IPC calls, so background refreshes do not keep a screen open. Two clocks agree on the limit: the page's own (it calls `auth.signOut` and shows "Signed out after N minutes of inactivity") and the main process's, which is authoritative: while there is input the page reports it (`auth.activity`, at most every 10 s) and `SessionState.lastActivityAt` restarts; `currentUser()` ends a session idle longer than the limit (the login row is closed as of its last activity), so even a stuck page or a phone that was closed is locked out of every call. The report's answer carries the limit and whether the session is still open, so a session ended on the main side locks the page too. It applies to paired phones as well (each device has its own session state and clock).

## Reports (sales summary)

`/reports` (nav "Reports", `reports.view`: managers and admins; migration `0010` gave it to everyone who could void/refund or manage users) shows a summary for one day or a range of local days (From / To date fields, today by default; the range never ends before it starts). `reports.sales(from, to)` -> `salesReport` (`electron/db/queries/reports.ts`, types in core `reports.ts`, `dayRange` is midnight to next midnight): sales (completed, not voided, refund orders apart), refunds, voids (by the day they were voided), net after refunds, taken by payment method (refunds negative, voided sales taken off), customer credit (put on account, interest, paid back by method) and items sold by name. It is a read-only summary so an admin can compare it with their own counts by hand: there is deliberately **no cash drawer, expected-cash or variance feature** (tried and reverted).

**Selector and export:** a select picks the report (`REPORT_KINDS`: Sales summary = all sections, Payments by method, Customer credit, Items sold). Each is a `ReportDocument` (core `report-document.ts`: titled sections of plain text rows, built by `buildReportDocument(kind, data, money)`), which the page renders and `reports.export(kind, from, to, format)` turns into a file in the main process (`electron/reports/export.ts`): **CSV** (`reportToCsv`: plain numbers, BOM for Excel), **PDF** (`reportToHtml` drawn in a hidden window and `printToPDF`, A4) and **Print** (the same page through `webContents.print`, i.e. the system print dialog, which also lists "Save as PDF" and any printer). CSV and PDF open a save dialog in Downloads; closing a dialog returns `{ ok: false, canceled: true }` and the page stays quiet. The PDF and print paths have not been run in a real window yet.

## Customer display (second monitor)

- A second window for the customer, showing what is scanned. **Settings > Customer Display > Show customer display** is a switch that shows or hides it now (on while the window is open; it follows the window being closed from its own title bar); Checkout has no control for it, it only keeps the window up to date. **Settings > Customer Display > Open on start** (`AppSettings.customerDisplayOnStart`, per device, storage migration 4) opens it when the app starts.
- The window is made by the main process (`electron/display/index.ts`, `registerCustomerDisplay` in `main.ts`; channels `display:*`, `DesktopApi.display`, API version 25). It is the same app loaded at `#/customer-display` (`CustomerDisplayPage`, `pages/customer-display/`): `App` sees that hash and renders only the router outlet there (no nav rail, banner or start-up work). It is created hidden and shown with `showInactive()` so the cashier's keyboard focus stays put, has no scanner attached (scans only reach the main window), and is closed when the main window closes.
- **What it shows** is a `CustomerDisplayState` (core): `idle` (no text: three dots slowly fading in turn, `data-idle`; still for reduced motion and read out as "Ready for the next customer"), `shopping` (lines with quantity × price, line totals, running total; the line added or changed last is highlighted and scrolled into view) and `paid` (thank-you, total, change, amount put on account; back to the idle screen after 10 s). Checkout computes it from its lines and publishes it on every change (`CustomerDisplayService.publish`); right after a sale it publishes `paid` until the next item is scanned or the order is cleared. The main process validates and keeps the latest state (`display/state.ts`) and sends it on, so a window opened mid-sale starts with what is on screen.
- **Remember monitor and position:** Settings > Customer Display > **Remember monitor and position** (`AppSettings.customerDisplayRemember`, default on, storage migration 7; API version 28, `display.show({ remember })`). Off: the window ignores the saved place and opens as on a first start (centred on a monitor other than the primary when there is one), and where it is moved to is not saved (the saved file is left as it was, so turning it back on brings that place back; turning it on while the window is open saves where it is now). It applies to an open window at once.
- **Window mode:** Settings > Customer Display > **Window mode** (Windowed, Maximized, Full screen; `AppSettings.customerDisplayMode`, default Windowed, storage migration 6; API version 27, `display.show({ mode })`). The mode is applied when the window opens, on the monitor it was on last (maximized and full screen cover that monitor), and also to an open window as soon as the setting changes (`CustomerDisplayService` calls `show` again). The remembered position is only updated while windowed; when maximized or full screen only the monitor is updated (`placementOnDisplay`), so the size and place it has as an ordinary window survive. Full screen has no window controls: turn the **Show customer display** switch in Settings off to close it.
- **Highlight the latest line (both screens, no timeout):** Checkout remembers the line added or changed last (`lastTouched`: a scan, Add, + / -, a typed quantity) and keeps it highlighted (`.row-target` on the row inside the swipe wrapper) and scrolled into view (`scrollToRow`) until another line is touched, the line is removed or the order is cleared or completed. It publishes that line's index as `CustomerDisplayState.highlight` (API version 26; the main process drops an index outside the lines), so the customer display shows exactly the same line highlighted and scrolls it into view (`block: 'nearest'`), wherever it is in the list. It does not guess by comparing lists, and a state published again with nothing new keeps the highlight.
- **Monitor and position are remembered** (`display/window-bounds.ts`, pure and unit-tested; stored in `userData/customer-display.json`, saved 400 ms after the window moves or resizes and on close): the monitor it was on and its position **relative to that monitor**, so it returns to the same spot if the monitors were rearranged. A monitor is found again by id, then by position and size, then by size alone (ids change when displays are reconnected). **It is always clamped inside the monitor's usable area** (`workArea`, not under the taskbar): made no larger than the area and moved so no edge is outside it, however the resolution or arrangement changed. With nothing saved, or when its monitor is gone, it opens centred (1024 × 768, smaller on a small monitor) on a monitor other than the primary one when there is one, else on the primary.
- **UI scale:** Settings > Customer Display > **UI scale** (75% to 300%, default 100%, `AppSettings.customerDisplayScale`, storage migration 5; a saved value outside the list is ignored). The display page applies it by setting the root font size of its window (everything there is sized in rem) and resets it when it goes away. The display window is a separate page sharing the same storage, so `AppSettings` listens for `storage` events and the display follows a change made in the till's window at once.
- Not built yet: a full-screen or kiosk mode for the display, customer names or loyalty on it, ads or idle slideshows, and on Linux/Wayland the window position cannot be read, so it opens where the compositor puts it.

## Checkout order draft

The order's items are a small table (`role="table"` grid, sticky title row Item / Quantity / Total; one column template `--cols` shared by the title and every line, with a fixed-width quantity column so the − / quantity / + controls line up down the list). Rows are `[data-row-id]` (specs select them that way, not `li`). The item name opens the product dialog (`ProductViewer`) for anyone with `catalog.view`. **Live catalog:** `CatalogService` reloads on `stock` data changes (every product write announces it) and checkout follows it (`followCatalog`): a changed price/name/unit is taken over with a banner, an item no longer for sale comes off the order; Complete Order still re-checks everything in the main process.

- The order in progress saves itself: every change to the lines is written (debounced 300 ms, flushed when the page closes) through `window.micropos.checkout.*` to the `settings` table under the key `checkout.draft` (`electron/db/queries/draft.ts`, `CheckoutDraftService` in Angular). It is restored when Checkout opens, including after an app restart. The main process validates whatever the renderer sends before storing it.
- In the ERD (`docs/erd.mmd`) the draft appears as the `checkout.draft` row of `settings`, with a dashed link to `products` (its lines hold product ids as JSON, with no foreign key). If drafts move to real `open` orders, update the ERD in the same change.
- It is one draft per register for now. Once employees sign in, move it to an `open` order (with its lines) per employee.
- **Clear vs Void:** *Clear* empties a cart that was never recorded and deletes the draft (confirmation dialog, no trace kept). *Void* is for a sale that was already recorded: it keeps the order with status `voided` and writes an audit entry so the books still add up (built: see Sales Orders). The checkout button is Clear.

## Banner (short status messages)

The strip slides in and **also animates out** (`animate.leave="banner-leave"`, 150 ms fade and slide up, in `styles.css`); `BannerHost` keeps its popover open for `LEAVE_MS` after the banner goes so the leave animation is seen.

- Use `BannerService` (`src/app/core/banner/`) for brief feedback instead of inline text: `banner.success('Bananas added')`, `banner.warning(msg, { duration: 'long' })`, `banner.error(...)`, `banner.info(...)`, or `banner.show(msg, { severity, duration, key })`. One thin strip at the top of the window (`BannerHost`, placed once in the root); click it to dismiss.
- Hovering a timed banner pauses its countdown (`pause()` / `resume()`, wired to the strip's mouseenter and mouseleave); after the pointer leaves it stays for what was left, at least 0.6 s. Persistent banners have no timer.
- Default duration is 1.5 s; presets `short` 0.8 s, `default` 1.5 s, `long` 4 s, `persistent` (stays until clicked or `dismiss()`), or any number of milliseconds. Default severity is `info`.
- **Persistent banners** (`duration: 'persistent'`, e.g. an impending update notice) are kept apart from the queue and stay until the system calls `banner.remove(key)` (or `dismiss()` / a click, unless `dismissible: false`). Timed banners show over them for their moment and the persistent one returns. While one exists, `reserveSpace()` is true and the app root sets `--banner-offset` (2.25rem): the root pads down by it, the nav rail starts below it, and any page that sizes itself to the viewport must use `calc(100svh - var(--banner-offset,0px) - ...)` so nothing hides behind the strip.
- Messages queue and show one at a time (at most 5 waiting; the oldest waiting ones are dropped). Pass a `key` for anything that can repeat quickly: the same key updates the banner on screen and restarts its timer instead of queueing again.
- The banner is a popover in the browser top layer so it sits above dialogs; it uses `keepOnTop` (`core/viewport/top-layer.ts`) with a `data-top-layer-priority` (banner 1). Any new always-on-top element needs a priority too, or the elements will keep re-raising each other.
- Severity colors (`success`, `warning`, `destructive`, `primary`) come from `@micropos/theme` tokens.

## On-screen keyboard

**Press feedback:** a key under the finger changes color and shrinks slightly for 140 ms (`flashKey` in `core/ui/key-flash.ts` on the panel's `pointerdown`, style `.key-flash button[data-pressed]` in `styles.css`), on the keyboard, its numpad and the numeric keypad, so a tap on a touch screen can be seen to register.

- Settings > "On-screen keyboard" (off by default, per device) turns it on; "Numpad beside keyboard" adds a numpad to the right of the QWERTY keyboard. Both live in `AppSettings` (a new setting needs a default and a `storage.migrations.ts` entry).
- It is attached at the lowest level: `OnScreenKeyboardService` (`core/keyboard/`, started in the root `App`) listens for focus on the whole document, so **no per-field code is needed**. Every `text`, `search`, `email`, `url`, `tel`, `password` input and every `textarea` gets the QWERTY keyboard (number row on top, one-shot Shift, a **#+= key at the bottom left that swaps the letters for a symbols page** (@ # $ _ & - + ( ) / * " ' : ; ! ? = % \ | [ ] { } < > ₱) and back with abc, Enter, Done). Every `type="number"` input, and any input with `inputmode="decimal"` or `"numeric"`, gets the numeric keypad (`core/keypad/`).
- Both float next to the focused field (below, else above, right or left, whichever fits; they are pushed back into view instead of clipping), as overlays in the top layer. Their keys never take focus from the field (kiosk focus rule) and edit it at the caret, firing `input`; Done blurs the field, which is what commits it. While open, the field's `inputmode` is set to `none` so an OS soft keyboard does not appear too.
- Number inputs are switched to `type="text"` while the keypad is up (a number field cannot show a half-typed "3.") and back afterwards; the keypad takes its limits from the field: `step` sets the decimals (none: whole numbers, `any`: 3), `max` sets the whole digits. `change` fires on close if the value changed. There is no minus key yet.
- Opt a field or container out with `data-no-keyboard`. To set digit limits explicitly on a text field use the `appOnScreenKeypad` directive (`[keypadWholeDigits]`, `[keypadDecimals]`); it marks the field `data-keypad` so the global service leaves it alone. Prefer the plain attributes (`type="number"`, `step`, `max`, `inputmode`) and let the service handle it.
- When adding a field, just use a normal input; check it in the app with the setting on.
