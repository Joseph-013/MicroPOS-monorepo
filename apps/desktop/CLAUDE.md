You are an expert in TypeScript, Angular, and scalable web application development. You write functional, maintainable, performant, and accessible code following Angular and TypeScript best practices.

## TypeScript Best Practices

- Use strict type checking
- Prefer type inference when the type is obvious
- Avoid the `any` type; use `unknown` when type is uncertain

## Angular Best Practices

- Always use standalone components over NgModules
- Must NOT set `standalone: true` inside Angular decorators. It's the default in Angular v20+.
- Do NOT set `changeDetection: ChangeDetectionStrategy.OnPush` explicitly. `OnPush` is the default in Angular v22+.
- Use signals for state management
- Implement lazy loading for feature routes
- Do NOT use the `@HostBinding` and `@HostListener` decorators. Put host bindings inside the `host` object of the `@Component` or `@Directive` decorator instead
- Use `NgOptimizedImage` for all static images.
  - `NgOptimizedImage` does not work for inline base64 images.

## Accessibility Requirements

- It MUST pass all AXE checks.
- It MUST follow all WCAG AA minimums, including focus management, color contrast, and ARIA attributes.

## Components

- Keep components small and focused on a single responsibility
- Use `input()` and `output()` functions instead of decorators
- Use `model()` for two-way bound properties with `[(prop)]` syntax instead of pairing `input()` with `output()`
- Use `computed()` for derived state
- Use `linkedSignal()` for state derived from multiple reactive sources that must stay synchronized
- Prefer inline templates for small components
- Prefer Signal Forms (`@angular/forms/signals`) for new forms. They are stable in Angular v22+ and provide signal-based state, type-safe field access, and schema-based validation
- When not using Signal Forms, prefer Reactive forms instead of Template-driven ones
- Do NOT use `ngClass`, use `class` bindings instead
- Do NOT use `ngStyle`, use `style` bindings instead
- Do NOT import `CommonModule`, import only the directives and pipes the template uses, such as `AsyncPipe` or `DatePipe`
- When using external templates/styles, use paths relative to the component TS file.

## State Management

- Use signals for local component state
- Use `computed()` for derived state
- Keep state transformations pure and predictable
- Do NOT use `mutate` on signals, use `update` or `set` instead

## Templates

- Keep templates simple and avoid complex logic
- Use native control flow (`@if`, `@for`, `@switch`) instead of `*ngIf`, `*ngFor`, `*ngSwitch`
- Use the async pipe to handle observables
- Do not assume globals like (`new Date()`) are available.

## Services

- Design services around a single responsibility
- Use the `providedIn: 'root'` option for singleton services
- Prefer the `@Service` decorator over `@Injectable({providedIn: 'root'})` for new singleton services (Angular v22+)
- Use the `inject()` function instead of constructor injection

## Electron / Forge (MicroPOS)

- Renderer: Angular, built to `dist/renderer` (`pnpm build:renderer`). No `<base href>` (a base tag makes the hash router rewrite the URL to the folder, which breaks reload over `file://`).
- Main/preload: `electron/*.ts`, compiled with `tsc -p tsconfig.electron.json` to `dist/electron` (CommonJS). `package.json` `main` points at `dist/electron/main.js`.
- Commands: `pnpm --filter @micropos/desktop start | build | package | make | typecheck | test`.
- DevTools open automatically, docked inside the window, whenever the app is not packaged (`!app.isPackaged`, covers `pnpm dev` and `pnpm start`); packaged builds never open them.
- Renderer has no Node access (contextIsolation, sandbox). The preload runs sandboxed and cannot `require` local files, so `build:electron` bundles `electron/preload.ts` into one file with esbuild after `tsc`. Keep the sandbox on; never import Node modules in the preload.
- Angular and `@micropos/core` are bundled into the renderer, so they live in `devDependencies`. `forge.config.js` sets `prune: false` and excludes `node_modules` because Forge's dependency walker can't resolve hoisted workspace deps. When adding native runtime deps (better-sqlite3), they must be shipped and unpacked from the asar; revisit this config then.
- **Installing over the first MicroPOS (Windows):** the earlier app was `micropos` 1.0.0 (Squirrel id `micropos`, `micropos.exe`, data in `%APPDATA%\micropos`: `micropos.db`, `logs/`, `user/logo`, plus Chromium's storage). This app takes the same identity (`productName: "micropos"`, the Squirrel maker's `name: 'micropos'` in `forge.config.js`) so Setup upgrades it in place, and its version must stay **above 1.0.0** (Squirrel launches the highest installed version, so an older number would keep running the old app). `electron/squirrel.ts` answers the installer events (shortcuts made and removed, the app exits); without it Setup would open windows and make no shortcuts. **Old data is wiped once:** `purgeLegacyData` (`electron/legacy-data.ts`, called first thing in `main.ts` for packaged builds only) removes everything in the user data folder unless it holds the marker `micropos-data.json`, then writes the marker; Chromium's own storage is cleared through `session.defaultSession.clearStorageData()` after that. From then on the folder is left alone. To force another clean start on a future install, raise `DATA_GENERATION`. Not run in development (the dev database lives in `local-data/`). Not testable on Linux beyond the unit tests (`legacy-data.spec.ts`); try a real Setup.exe on a Windows machine that has the old app.
- **Version bump with every update:** whenever a new update of the desktop app is made (anything that will be built and installed), raise `version` in `apps/desktop/package.json` in the same change: patch for fixes, minor for new features, major for breaking changes or a data reset (`DATA_GENERATION`). Squirrel only upgrades to a strictly higher version, and it launches the highest one installed, so an update without a bump is never picked up. Never lower it (see the first-MicroPOS note above: it must stay above 1.0.0). **Claude does the bump:** when finishing an update, choose the level, change the version, commit it on its own ("Bump version to x.y.z") and say the new version in the report; the user does not have to ask. The bump goes once per update that ships: if the current version has not been released yet (the user says so, or it was bumped earlier in the same unreleased batch), fold the work into it instead of bumping again. When unsure whether the current version has shipped, ask once.
- Not containerized (see `.dockerignore`).

## UI conventions (MicroPOS)

- Copy: titles and labels are short, professional, sentence case ("Checkout", "Sales Orders"). No descriptions, subtitles or helper text unless critically necessary, e.g. confirmation dialogs.
- Shape: square and boxy everywhere. No `rounded-*` classes; the theme radius is 0. Only radio buttons stay circular (as in the design). Dialogs are square with the `blueprint` corner marks; only confirmation (alert) dialogs carry a description.
- Scrollbars are styled globally in `styles.css` (slim, square, no arrows); don't restyle them per component.
- Keep borders minimal: corner marks (`blueprint`) are for large panels only. Repeated items (grid cells, list rows) get a single hairline border with no marks and no outlined tags (`before:hidden`, `tagNeutral`).
- Destructive actions (Delete, Clear, Remove) use the `destructive` variant on the button, the menu item (`variant="destructive"`) and the confirming alert-dialog action. Restore and other safe confirmations stay default. Exception: the Clear button beside Complete sale on Checkout stays neutral (outline) so it does not draw the eye next to the main action; its confirmation dialog's Clear action is still destructive.
- Space is at a premium: keep page padding tight (main content uses `p-3`) and put titles close to the edges.
- Styles are plain CSS (Tailwind v4 via PostCSS), not Sass; global styles live in `src/styles.css`.
- Kiosk behavior: text selection is off app-wide (`html { user-select: none }` in `styles.css`). Inputs and textareas stay selectable; opt other text in with Tailwind `select-text` or `select-all` (order numbers, receipt text, error messages).
- Minimum window is 1024 × 400 (`MIN_WINDOW` in `core/viewport/too-small-overlay.ts`); below it a full-window warning covers the app. Design layouts for that minimum.
- Touch sizing lives at the root: `--control-height` (44px), `--control-height-sm` (36px), `--control-height-lg` (56px) and `--popup-offset` in `src/styles.css`. Buttons, inputs, selects, tabs, and menu/list rows read them, so one edit resizes the app. Do not set `h-*`/`size-*` on a control in a page; use the component's `size` input (`size="lg"` for primary actions). New or newly generated Spartan components must use these variables instead of fixed heights.
- Required fields: label them with a red asterisk, not "(required)" text: put `data-required` on the `<label hlmLabel>` (styles.css adds the asterisk). Only mark fields that must be filled; optional ones stay plain.
- Forms are draftable: a dialog form that takes more than a moment to fill in saves its progress as a draft (see Form drafts under Products page: debounced save, restored with a "Draft restored" banner, Close instead of Cancel, Reset, cleared on save) so leaving the page or restarting loses nothing. If a form seems too small to need one, ask the user before leaving it out.
- Touch first: keep targets comfortable (nav rail is 3.5rem collapsed with 40px rows).
- Colors and fonts come from `@micropos/theme` tokens (Tailwind classes such as `bg-primary`, `text-muted-foreground`); don't hard-code values.

## Table design

The Products table (`pages/products/`) is the reference; build every data table the same way.

**Layout**
- A CSS grid with table roles (`role="table"`, `rowgroup`, `row`, `columnheader`, `cell`), not a `<table>`, so each row can sit inside `app-swipe-actions`. One column template (`COLUMNS_TEMPLATE`) is shared by the title row, the filter row and every body row. The table has a `min-w-*`; the area around it scrolls both ways and has no side padding (swipe actions stick to its visible edge).
- The header is sticky and has two rows. **Row 1** holds the column titles: each is a button that sorts by that column (click once ascending, again descending) with a direction arrow (`lucideChevronsUpDown` when idle) and `aria-sort`. **Row 2** holds the filter for that column, directly above the data it filters. Example: the Name column is "Name ^" over a text input; the Categories column is "Categories ^" over a select. There is no separate search or filter bar above a table, and the header with its filters stays visible when no rows match.
- Filter controls fit the column: text input for names and codes, combobox or select for categories and status, a from/to date range (native date inputs) for dates, a range for numbers. Text and date filters use `app-filter-input` (`core/ui/filter-input.ts`: a button group, the input joined to an x clear button that is disabled while the field is empty); comboboxes use `showClear` (hidden while on "All"). Filters are compact (the filter row sets `--control-height` to the small size) and have placeholders. Columns with nothing to filter leave their filter cell empty. Date range filters treat a first date as a single day (the end date follows it); change or clear the end to widen it, and a cleared end means "from then on". Filters on different columns combine (AND).
- **Leftmost column is selection**: a checkbox per row, and the title-row checkbox selects every visible row (shows a dash while only some are ticked). The filter-row cell under it holds a **Reset filters** icon button (disabled when no filter is set). Selection counts the rows that match the current filters, on any page: it survives changing pages, Shift ranges follow the filtered list across pages, and a filter never leaves a hidden row selected for a bulk action to hit. The header checkbox ticks (or unticks) only the rows of the current page, shows a dash while only some of them are ticked, and leaves other pages' selections alone; there is deliberately no "select every row on every page" action. Selection works like a file explorer (`RowSelection`, `core/ui/row-selection.ts`): **Ctrl/Cmd + left click** on a row toggles it, **Shift + left click** selects the range from the last row clicked (replacing the selection; with Ctrl too it adds to it), and **Shift + click on a checkbox** ticks the range. A plain click opens the row as before. Ranges follow the filtered, sorted list (across pages).
- Default sort is by created date, newest first; empty values (no SKU, no cost) always sort last. Money columns are right-aligned. Status columns use a badge: `success` (green) for active, `destructive` (red) for inactive, `outline` for deleted.
- Small text for long codes (SKU `text-xs`), muted color for secondary columns, truncate long values.

**Row actions** (every route offers the same actions)
- Bulk buttons appear in the page header when rows are ticked ("N selected", then the actions that apply, then Clear).
- Right-click (or long-press) context menu on the row; if the row is part of a multi-row selection the action applies to the whole selection (single or bulk). Delete is destructive-styled; menu items that would change nothing are not offered. Status changes read "Set" followed by the badge the row will get (`Set [Active]`, `Set [Inactive]`).
- Swipe left on a row (touch): icon-only action (the shared swipe component; red with a white icon for delete, green for restore). Mouse and keyboard users have the menu and buttons.
- Delete and restore always show a confirmation dialog, whichever route started them. The dialog lists what it is about to act on (`app-confirm-items`: every name, with a secondary detail such as the SKU), for one row as well as for a bulk selection. Status changes and other easily undone edits apply at once with a banner.
- Deleted rows are reached through a "Deleted only" switch in the page header (swaps the list; the normal list never mixes them); they are dimmed, read-only, and can be restored.

**Paging and highlighting**
- Every table has a footer (`app-pager`, `core/ui/pager.ts`): "26–50 of 120", rows per page (25, 50 default, 100), first / previous / next / last and "Page n of m". It is offset paging over the already filtered and sorted list (`Pager`: page `n` = rows `n * size` to `(n + 1) * size`), and goes back to page 1 when a filter, the sort or the page size changes. All data is still loaded into the renderer and sorted and filtered there, which is fine for the catalog tables; when Sales Orders gets big, move its sort, filter and paging into the main process (`orders.list({ ..., offset, limit })` returning rows and a total) without changing the footer.
- **Highlight, don't select:** a row that is the target of a link or of the dialog being shown gets `.row-target` (tinted with an inset accent bar; `styles.css`), separate from the selection checkbox. Put the class on the `role="row"` element **inside** `app-swipe-actions`, not on the outer wrapper: the swipe component paints an opaque `bg-background` over the wrapper, which hides a tint there (selected rows use `bg-muted` on the inner row for the same reason). Each page has a `target = rowTarget()` (`core/row-target.ts`) set when a dialog opens for a row (edit product or category, view an order, adjust a batch) or a link names one. The highlight lasts 6 s (`ROW_TARGET_MS`) and then goes away on its own; targeting a row again restarts the clock. Rows carry `data-row-id` on the wrapper; `scrollToRow` (`core/row-target.ts`) scrolls to it once it has rendered, retrying for up to 2 s.
- **`?highlight=<row id>`** on a table page shows the page holding that row and highlights it (`Pager.showItem`); filters that hide the row are cleared first. Implemented on Sales Orders (the order dialog's external-link button goes to `/orders?highlight=<order id>`); the parameter is removed once used. `?view-sales-order=<id>` and `?edit-product=<id>` also show the target's page and highlight it.

**Motion**: rows fade in and out (`animate.enter` / `animate.leave` with `row-enter` / `row-leave`, 0.1 s), and a row whose data changed flashes the accent color briefly (`row-flash`); all in `styles.css`. Rows do not animate on the first load.

## Barcode scanner

- **Scale labels:** Checkout first looks for a product whose barcode/SKU equals the scanned code; failing that, a 13-digit code starting with 2 with a valid check digit is read as a scale label (`parseScaleBarcode` in core, layout `2 PPPPP 0 WWWWW C`: PLU and weight in grams). The weighed product whose code is that PLU is added with that weight (converted to its unit); a second label for the same product adds to the line. Labels that carry a price instead of a weight, or other layouts, need a store-level layout setting (not built).

- USB keyboard-wedge scans are detected in the **Electron main process** (`electron/scanner/`), in front of the page, so a stray scan can never reach the UI. `attachScanner(win)` (called in `main.ts`) hooks the window's `before-input-event`. `ScanGate` holds every printable key back for one speed threshold (35 ms): if the burst turns out to be a scan (`BurstDetector`: min 3 chars with Enter, 6 without; printable ASCII so 2D payloads work) the held keys are discarded, the closing Enter is swallowed and the code is sent to the page as `scanner:scan`; if it was a person typing, the held keys are replayed to the page in order (`sendInputEvent`), so typing is delayed by at most 35 ms. Shortcuts (Ctrl/Alt/Meta), Tab, arrows etc. pass straight through. Shift/CapsLock never disturb a burst.
- Because the scan's keys are never delivered, nothing can leak: no text in fields, no Space pressing a focused button or checkbox, no Enter reopening a dialog trigger, whatever has focus. The renderer has no keyboard listener for scans any more.
- The renderer (`src/app/core/scanner/`): `ScannerService` (started at the root) subscribes to `window.micropos.scanner.onScan` and only decides who gets the code. Without the Electron bridge (plain browser) no scans arrive. `scanner.enabled` is forwarded to the main process (`scanner.setEnabled`); off lets scanner keys through as ordinary typing.
- Take control with a claim: `claimScanner(handler)` in a component or dialog (released on destroy), or the `appScannerClaim` directive with `(scan)`. The newest claim gets scans; releasing it returns control to the previous one. A handler can return `false` to pass a scan down.
- To let a text field receive scans (e.g. a barcode lookup), put `appScanInput` on it (`(scan)` emits the code). While it is focused the scan sets its value to the code (firing `input`), and claims do not get that scan. Fields without it never receive scanned text.
- Tests: the gate and detector are pure and tested with a fake clock in `electron/scanner/*.spec.ts` (`pnpm test:db`). In page specs, stand in for the scanner with `TestBed.inject(ScannerService).receive(code)`. Note that CDP and `sendInputEvent` key events bypass `before-input-event`, so the main-process path can only be exercised with real keyboard input.
- Changing anything under `electron/scanner/` needs a restart of `pnpm dev`.
- `KioskFocusService` stops mouse/touch presses on buttons from taking focus (clicks still work), so focus stays on the field a scan should go to. Add `data-allow-focus` to anything that must take focus.

## Database (SQLite + Drizzle)

- Main process only (`electron/db/`); the renderer reaches it over IPC. Schema is one file per table in `electron/db/schema/` (exported from `schema/index.ts`). Conventions: UUIDv7 text ids (`uuid7()`), money in integer cents, timestamps as epoch milliseconds, soft delete via `deleted_at` on catalog/people tables, orders are never deleted (void or refund instead), a partial unique index for any unique field on a soft-deletable table, and an index on every foreign key.
- Change workflow: edit the schema, run `pnpm db:generate` (writes a new SQL file in `electron/db/migrations/`; commit it, never hand-edit a shipped migration). The history was squashed into one `0000` migration before any release, so a database made earlier (e.g. the dev one) must be rebuilt with `pnpm db:migrate --fresh --seed`; once a build ships, migrations are append-only again. Pending migrations are applied automatically when the app opens the database; packaged builds ship them via Forge `extraResource`.
- Commands (work from the repo root or `apps/desktop`; modeled on Laravel): `pnpm db:migrate` applies pending migrations; `pnpm db:migrate --fresh` drops every table, migrates from scratch and creates one admin account; `pnpm db:migrate --fresh --seed` also runs the factories; `pnpm db:seed` runs the factories only (refuses a database that already has a catalog); `--database=<file>` targets another file. The default file is `apps/desktop/local-data/micropos-dev.db`, which is also what the unpackaged dev app opens (packaged builds use the per-user data folder). Close the dev app before `--fresh`, then restart it.
- The bootstrap admin (`seeders/admin.seeder.ts`) is employee number `1001`, PIN from `MICROPOS_ADMIN_PIN` or the dev default `1234`. Dev tooling only: the CLI is not shipped in packaged builds.
- PINs are stored only as scrypt hashes (`electron/auth/pin.ts`).

### Factories and dummy data

- `electron/db/factories/` builds consistent dummy data (faker): employees, catalog, sales with lines and payments, voids, refunds, login sessions, audit entries, settings. Dev-only: not shipped in packaged builds and never imported by production code paths.
- **When the schema changes, check the factories.** New or renamed columns, new tables, changed constraints or enums (employee roles, order statuses, payment methods) usually need a matching change in the builders (`*.factory.ts`) and in `seed.ts` (insert order, FK order, totals that satisfy CHECK constraints). Update them in the same change.
- **Known barcodes:** the seeded catalog starts with one product per code in `factories/known-barcodes.ts` (a printed test sheet of real EAN-13 codes), with faker names, prices and tracking, followed by the hand-written sample products and random extras. The `480...` codes are the product barcode as they are. The `2...` codes are variable-weight scale labels (`2 PPPPP 0 WWWWW C`): the product is seeded as a weighed one (kg) whose code is the 5-digit PLU without leading zeros (`scalePlu`), not the whole label. Add new sheet codes to that file (a test checks every check digit).
- Verify with `pnpm test:db` (runs migrations on a temp database, seeds it, and checks constraints, totals, payments and foreign keys). Add a test for any new rule.
- Seeding is done through the commands above (`--seed`). Factories reuse the existing admin instead of creating another. Dummy sign-ins: `1001` (admin), `1002` (manager), `1003`+ (cashiers); dummy PIN `1234`.

## IPC bridge (renderer to database)

- The renderer never touches SQLite. It calls `window.micropos` (typed as `DesktopApi` in `@micropos/core`), exposed by the sandboxed preload (`electron/preload.ts`), answered by `ipcMain.handle` handlers in `electron/ipc/`. In Angular, inject `DESKTOP_API` (`core/api/desktop-api.ts`) or a service built on it, such as `CatalogService`; tests provide a fake `DESKTOP_API`.
- Adding a call: (1) add the DTO and method to `packages/core` (`catalog.ts`, `desktop-api.ts`) and rebuild core; (2) write the query as a plain function in `electron/db/queries/` and test it in `db.spec.ts`; (3) add the channel to `electron/ipc/channels.ts`; (4) register the handler in `electron/ipc/index.ts`; (5) expose it in `electron/preload.ts`; (6) use it from a service. Handlers stay thin: validate input, call the query, return plain data.
- Contract version: `DESKTOP_API_VERSION` (`@micropos/core`) and `API_VERSION` (`electron/ipc/channels.ts`) must be equal (a test enforces it). Bump both when a call or payload changes in a way an older main process cannot handle. At startup the page asks the main process for its version (`DesktopApiGuard`); on a mismatch, or an old main that does not answer, a persistent banner says to restart the app. In development the page hot-reloads but the main process does not, so **restart `pnpm dev` after any change under `electron/`** or to `packages/core` (the dev script clears the Angular dev-server cache on start, which otherwise keeps a stale pre-bundled copy of core and shows "out of date" even when both sides match).
- DTOs in `@micropos/core` are types only (the CommonJS main process imports them with `import type`).
- For the dev app, run `pnpm db:migrate --fresh --seed` first so there is data to read.

## Products page

- `pages/products/` lists every live product (active or not) from `ProductsService` (`window.micropos.products.*`, queries in `electron/db/queries/products.ts`); Checkout still reads active products only through `CatalogService`. Rows open an add/edit dialog (`ProductForm`, opened with `HlmDialogService`); Delete asks first and soft-deletes.
- Validation lives in the main process (`sanitizeProductInput`, duplicate SKU/barcode check); a rule violation returns `{ ok: false, field, error }` and the form shows it under that field. Prices are typed in pesos and stored as cents (`core/money-input.ts`).
- **Sold by / weighed products:** `products.unit` is `each` or a weight unit (`kg`, `g`, `lb`, `oz`); the price and cost are per that unit and the checkout quantity is the weight (decimal, stored as thousandths). Adding a weighed product at checkout opens its weight field at once; adding it again edits that weight instead of adding a unit. A draft line carries its `unit`.
- **One code field:** barcode and PLU are one column, `barcode` (shown as "Barcode / PLU" in the table and filter; the product form labels it "Barcode" for a product sold by Each and "PLU" for one sold by weight): packaged goods have an EAN, loose goods a short PLU, rarely both. SKU stays separate (your own stock code). No product needs a code (a weighed one without can still be tapped at checkout, it just cannot be scanned or keyed in). Seeded counted goods get an EAN, weighed ones a 4-digit PLU. In the Products table a PLU (4 or 5 digits, `isPlu` in core) is shown in italics and a barcode in regular type. Reading variable-weight barcodes (prefix `2` + item code + weight) is not built yet.
- **Delete and restore:** a leftmost select column (header checkbox selects every visible row) feeds bulk Delete / Restore buttons in the page header; a row can also be deleted or restored from its right-click menu or by swiping it left. All routes go through one confirmation dialog (`ask()` in `products.ts`), always shown. Acting on a row that is part of a multi-row selection applies to the whole selection. Restore skips a product whose SKU or barcode a live product has since taken and names it in a banner. The "Deleted only" switch swaps the list to just the deleted products (and the normal list hides them); deleted rows cannot be edited.
- The Products table is a CSS grid with table roles (`role="table"`, `row`, `cell`), not a `<table>`, because a row has to be wrapped in `app-swipe-actions` to be swipeable and `<tr>` cannot be wrapped. The title row, filter row and body rows share one column template (`COLUMNS_TEMPLATE`).
- **Scanner:** the page claims the scanner: a scan resets the filters and sets the Barcode / PLU filter to the code, with a warning banner when nothing matches. While the product form is open it claims the scanner instead and a scan fills its Barcode / PLU field (typed straight into it when that field is focused via `appScanInput`, and put there from any other field of the form, never into the name or SKU), so the table behind never changes and barcodes need no manual typing. The row's Enter handler still ignores a `defaultPrevented` Enter, a harmless guard now that the main process swallows a scan's keys.
- **Form drafts:** the add/edit product form saves itself like the checkout order: every change (debounced) is written to the `settings` table under `product.draft.new` (adding) or `product.draft.<product id>` (editing), via `window.micropos.products.*Draft` and `ProductDraftService`. Closing the dialog (the button reads Close, not Cancel), going to another page to make a category, or restarting keeps it; opening the form again restores it with a "Draft restored" banner (categories deleted meanwhile are dropped). Saving or deleting clears it; **Reset** (shown once something changed) puts the fields back and drops it. A form equal to its starting values has no draft. The page reads the draft before opening the dialog and passes it in the dialog context.
- Gotcha: a dialog opened through `HlmDialogService` must pass its own `id`. Its auto id (`brn-dialog-N`) can equal the id of an `<hlm-alert-dialog>` or `<hlm-dialog>` inside it, which throws "Dialog with ID ... already exists" and the inner dialog silently never opens.

## Categories page

- `pages/categories/` follows the Table design rules (select column, sortable titles, name and created-date filters, default newest first, Reset filters, "Deleted only" switch, row fades). Columns: Name, Products (live products in it, a link to Products filtered to that category via `?category=`), Order (`sort_order`, lower first where categories are listed in order) and Created.
- Add / edit in a dialog (`CategoryForm`, opened with its own dialog id `category-form`); Delete there, in the row menu, by swipe or in bulk always asks first. Delete is a soft delete: the product links stay, so a restore brings the category back with its products. Restore skips a category whose name a live one now uses and names it in a banner. Names are unique ignoring case (`queries/categories.ts`).
- Changes refresh `CatalogService` too, which feeds the checkout filter and the product form's category list.

## Inventory (batches and expiry)

- `products.tracking`: `none` (stock not tracked), `quantity` (one unnamed batch), `batch` (lot numbers) or `expiry` (lot numbers and expiry dates, plus an optional `shelf_life_days` that pre-fills the date when stock arrives). Set it in the product form ("Track stock").
- Stock lives in `product_batches` (one per delivery; unique per product and lot) and the append-only `stock_movements` ledger (`receive`, `sale`, `refund`, `void`, `adjust`, `waste`, `expired`, `repack_out`, `repack_in`; a CHECK ties each type to its sign). **Quantity on hand is never stored: it is the sum of a batch's movements**, so history is complete and refunds simply add stock back. Changing stock means inserting a movement (`receiveStock`, `adjustStock`, `allocateSale`, `restockSale` in `electron/db/queries/inventory.ts`), never editing a number.
- **Repackage** (opening a pack: a sack into loose kilos, a sack into smaller bags; `repackageStock` in `queries/inventory.ts`, `inventory.repackage` over IPC, `RepackageForm`): takes a quantity of a source product out of its batches (first-expiring-first-out, never expired ones) as `repack_out` movements and adds each target as `repack_in` movements, all sharing a `repackage_id`. Each side is typed in its own unit, so a loss is just a smaller target quantity; no pack size is stored on products. Target batches keep the source batch's lot number and expiry (a source without a lot gets `REPACK-yyyymmdd`; a source with no expiry needs one typed when the target expires), and the cost of what was taken is split over the targets by retail value (quantity x price). The whole thing is one transaction. Offered from Inventory (header button, batch menu) and the Products row menu. It is not waste: waste and expiry reports ignore `repack_*`. The form is draftable: one draft in `settings` under `repackage.draft` (`queries/repackage-draft.ts`, `InventoryService.*RepackageDraft`), restored on opening (it wins over the product the dialog was opened from), Reset drops it, saving clears it.
- Selling (`allocateSale`) takes stock first-expiring-first-out (no-expiry batches last, then oldest received), never from an expired batch, and returns the average cost of what it used to store in `order_lines.unit_cost` (margins stay right after costs change). A sale line's movements show which batches it drew from (recalls). **Checkout's Complete sale is not built yet, so nothing calls `allocateSale` outside tests and the seed data**; wire it (and `restockSale` for refunds and voids) when sales are recorded.
- UI: the Inventory page (`pages/inventory/`, under Items) lists batches as a table per the Table design rules (status: Expired / Expiring soon / OK / No expiry / Empty, "Show empty" switch, write-off by bulk button, row menu or swipe with a confirmation). Receive stock (header button, or the Products row menu; a scan picks the product) and Adjust stock (click a row: waste, expired, or a count correction) are dialogs. Products shows a Stock column (quantity, Out, Expiring/Expired) with a stock filter. `EXPIRY_WARN_DAYS` (3) in `@micropos/core` sets "expiring soon".
- Items > Overview (`pages/inventory-overview/`, `inventory.overview()` → `inventoryOverview` in `queries/inventory.ts`) summarises it: stock value at cost and retail, expired and expiring-soon batches with their cost, out-of-stock products, waste written off in 30 days, a Needs attention list and recent ledger activity. Its alert tiles link to the filtered lists (`/items/inventory?status=expired|soon`, `/items/products?stock=out`; both pages read those query params once on open).
- **Edit product from Receive stock:** the product list there includes products that track no stock (marked Not tracked); picking one shows "Stock is not tracked" with Receive disabled. Once a product is chosen an **Edit product** button opens its form over the dialog (with its saved draft), so tracking can be raised to batch or expiry and the lot and expiry fields appear without visiting Products. A scan for a product that does not track stock picks it the same way.
- **Receive another:** a checkbox in the Receive stock footer keeps the dialog open and clears the form after each receipt (a banner names the product received, the Cancel button becomes Close), so products can be scanned and received one after another. The choice is not remembered between openings.
- Expiry dates are entered as dates and stored as the end of that local day (good through the printed date). Packs that print only a month (EXP 11/2026) are entered with the Date / Month toggle in Receive stock; a month is stored as the last day of that month. No precision is kept, so such a batch shows as that last day.

## Completing an order

- *Complete Order* calls `checkout.completeOrder` (`electron/db/queries/orders.ts`): one transaction that writes the `orders` row (numbered SO-1001, SO-1002, ...), its `order_lines`, the `payments` row (cash records tendered and change) and the `sale` stock movements (FEFO, never expired batches, line cost from the batches used), then deletes the `checkout.draft` row. Any failure rolls it all back (`Rollback` sentinel, as in Repackage).
- Payment methods are `cash`, `card`, `ewallet`, `bank_transfer` and `other` (`ORDER_PAYMENT_METHODS` in core, `PAYMENT_METHODS` in the schema; a test keeps them equal, and `payments.method` is plain text so a new method needs no migration). Only cash takes money handed over and gives change; card, e-wallet and bank transfer take an optional reference number, and a refund reverses the payment with the same method.
- The renderer sends only product ids, quantities, the price it showed, the discount and the payment. Names and prices stored on the order come from the catalog. A product that is gone or inactive, a changed price or short stock refuses the whole order with per-line problems; the page then refreshes changed prices, drops unavailable items and keeps the rest so the cashier looks again. Products with tracking `none` have no stock check. Stock cannot go below zero.
- Until sign-in exists, sales are attributed to the first active employee, or to a "Register" employee created on first use (its PIN hash is invalid, so nobody can sign in as it). Switch to the signed-in employee when sign-in is built.
- Not built yet: order discount entry (the field is always 0), receipts, partial refunds, customer prepayments and balance adjustments (the `adjustment` ledger type exists but nothing writes it).

## Sales Orders

- The page (`pages/orders/`) lists every recorded order, newest first, built like the other tables (sortable titles, a filter under each: order number, date range, cashier, payment, status). It has the same selection column and gestures as the other tables; the bulk buttons are **Void N** and **Refund N** (counting only the selected completed sales). A row opens the order; right-click offers View. Void and refund are not built.
- **Void and refund** (`voidOrder` / `refundOrder` in `electron/db/queries/orders.ts`, `OrderActions` in `core/order-actions.ts`, `OrderActionForm`): only a completed sale (`canReverseOrder` in core: status completed and not itself a refund order) can be reversed, once, and always through a confirmation that lists the orders, shows the refund total and requires a **Reason** (up to 200 characters, kept in the audit log with who did it; this tiny form has no draft). Both run in one transaction and put the stock back into the batches it came from (`restockSale` writes `void` / `refund` movements; a sale whose stock was already returned is never returned twice; products that do not track stock have none). A **void** keeps the order, marks it `voided` and leaves its payments as history. A **refund** records a new completed order with negative lines, subtotal, total and payments (same methods, linked by `refundOrderId`/`refundOfOrderId`), numbered from the same SO- sequence, and marks the sale `refunded`; the whole order is refunded (no partial refunds). Refund orders show a **Refund** badge (and their own status filter), and the order dialog links the sale and its refund ("Refund of" / "Refunded by"). Entry points: the order dialog footer (Void, Refund), the table's bulk buttons and the row context menu (which acts on the whole selection when the row is part of it). The acting employee is the first active one until sign-in exists (see Completing an order).
- **`?view-sales-order=<order id>`** on any page opens that order in a dialog (`SalesOrderForm`, view mode) over the current page. `SalesOrderViewer` (`core/sales-order-viewer.ts`, started by `App`) watches the address, loads the order (`orders.get`) and opens or closes the dialog to match; closing removes the parameter (replacing the history entry, so Back does not reopen it); an unknown id shows an "Order not found" banner and clears the parameter. Both this and `?view-product` are `ParamDialogViewer`s (`core/param-dialog-viewer.ts`) and can be open together, each with its own parameter. To link to an order call `viewer.open(id)` or use a `routerLink` with that query parameter. Over any page except `/orders` the dialog footer has an icon-only external-link button (`lucideExternalLink`, "Open Sales Orders") (going there drops the parameter, which closes the dialog). The form takes `mode: 'view'` in its dialog context; add edit modes there when needed.
- **`?edit-product=<product id>`** on the Products page opens that product's edit dialog (`ProductsPage.openById`). The product is looked up by id (`ProductsService.find`), so it opens whatever the table's filters show; the row is flashed and scrolled to when visible. Unlike `view-sales-order`, the parameter is consumed at once (replaced out of the address) because the product form manages its own dialog. A deleted product shows a "was deleted" banner instead (deleted products are read-only). The tables are not paginated; if Products ever is, find the row's page with a count of rows sorting before it (offset paging).
- **`?view-product=<product id>`** on any page opens a read-only product dialog (`ProductView`, `ProductViewer`) over the page, deleted products included; it shows price, PLU or barcode, SKU, how it is sold, cost, stock, next expiry and categories. In the sales order dialog a line's product name opens it (on top of the order, which stays open) and a small link button beside the name goes to the product on the Products page; the product dialog has the same link as an icon button in its footer (not shown while already on Products). The link is `/items/products?highlight=<id>`: the Products page shows the page holding the product, highlights the row, clears filters that hide it and switches to Deleted only for a deleted product. Following it drops every dialog parameter, so all the dialogs close. Lines whose product was removed for good stay plain text.
- **`?new-product=<barcode>`** on any page opens the add-product form (`ProductForm` with a `prefill` context, `NewProductViewer`, a `ParamDialogViewer`) over the page with that barcode filled in and stock tracked by quantity, so a product can be created where it was found missing without visiting Products. A prefilled form keeps no draft (it would clobber the Products page's own add-form draft). Receive stock uses it: a scan for a code no product has shows "Create product"; once the product is saved the form picks it (a code that belongs to a product that does not track stock says so instead). Link to it with `NewProductViewer.open(code)`.
- Banners can carry an action button (`banner.success(text, { action: { label, run } })`); it sits right beside the message (the pair is centered), and pressing it runs the action and dismisses the banner. Checkout uses it for **View** after Complete Order (6 s instead of the usual long duration, so there is time to press it).

## Customers and credit (store credit, partial payments)

- A **customer** (`customers`: name, phone, note, optional credit limit; soft delete) can buy on account. What they owe is the sum of their **ledger** (`customer_ledger`, append-only like the stock ledger, never edited): `charge` (the unpaid part of a sale, positive), `payment` (money received, negative), `refund` and `void` (cancelling the charge of a credit sale, negative) and `adjustment` (either way, reserved; nothing writes it yet). A CHECK keeps each type's sign right. Positive balance = the customer owes the store; negative = the store owes them (a refund after they had paid off the debt). There are no per-order allocations: payments go to the account, not to a particular sale.
- **Credit sale** (`completeOrder`): `customerId` plus `amountPaid` (cents paid now, 0 to the total; omitted = the whole total). The payment row holds only what was paid (none when 0; cash `tendered` only has to cover `amountPaid`, and change is worked out from it), `orders.customer_id` links the sale (also when it was paid in full) and a `charge` entry puts `total - amountPaid` on the account. Without a customer the whole total must be paid. A customer's credit limit is enforced inside the transaction (balance + charge may not pass it); a deleted customer cannot be used. Checkout shows a **Customer** combobox and, once one is chosen, **Pay now** (default the whole total) with the amount **On account**, the customer's balance and limit, and refuses a charge over the limit; the customer is cleared after each sale.
- **Receive payment** (`receivePayment`, the customer account dialog): amount (never more than they owe; a bigger amount is almost always a typo, and prepayments are not supported), method (`ORDER_PAYMENT_METHODS`) and an optional reference; it writes a `payment` entry by the acting employee (see Completing an order).
- **Void and refund** a credit sale cancel what it left on account (`void` / `refund` ledger entry for the charged amount; a refund's entry is attached to the refund order, whose `customer_id` is the same). The paid part is returned as before (negative payments).
- **Customers page** (`pages/customers/`, route `/customers`, nav rail "Customers"): the standard table (selection gestures, paging, highlight, `?highlight=<id>`) with Name, Phone, Owes (red; "Credit" when negative), Limit and Last activity, a balance filter (Owes, Settled, Has credit), add/edit/delete (a customer with a balance cannot be deleted; the bulk Delete counts only those without one) and Deleted only/Restore. A row opens the **account dialog** (`CustomerAccountForm`, `?view-customer=<id>` via `CustomerViewer`, a `ParamDialogViewer`): balance, limit, phone, note, a **Receive payment** form (amount with a Full balance shortcut, method, reference), Edit, and the ledger newest first, each entry with what was owed right after it and sale numbers that open the order over the dialog. Sales Orders has a **Customer** column (with what went on account) and filter, and the order dialog shows the customer (opens their account) and the On account amount.
- Seed data (`customer.factory.ts`, `seed.ts`): six customers; about 15% of completed sales are credit sales (part paid, the rest charged within the limit), followed by some payments, so the pages have balances to show. The ERD (`docs/erd.mmd`) has `customers`, `customer_ledger` and `orders.customer_id`.

## Purchasing (suppliers, purchase orders, paying later)

- A **supplier** (`suppliers`: name, phone, note; soft delete) is who the store buys from. A **purchase order** (`purchase_orders`, numbered PO-1001, ...; `purchase_order_lines`: product, quantity, unit cost; `purchase_payments`) records stock ordered in advance and paid later or in parts. Status: `ordered` (placed, not here), `received`, `cancelled`. Optional expected delivery date, payment due date and the supplier's own reference. **What is owed = total - sum of payments** (0 for a cancelled order); supplier balance is the sum over their orders. No ledger: payments are tied to the order they pay.
- `electron/db/queries/purchases.ts`: `createPurchase` / `updatePurchase` (only while `ordered`; lines are replaced, a product appears once, the total may not drop below what is paid), `payPurchase` (deposit allowed before arrival; never more than owed; `purchase_payments` is append-only, amount CHECK > 0), `cancelPurchase` (only `ordered` with nothing paid), `receivePurchase`.
- **Receiving a delivery** (`receivePurchase`, the order dialog's Receive stock = a **receiving session**, `PurchaseReceiveForm`): each line shows what is left; scan a product (counts one as arrived) or type the quantity, or **Everything left**; lot and expiry appear for a line once something arrives. Receive first checks the entries (quantities, lot, expiry) and then asks for confirmation, listing what goes into stock (or saying nothing will, for an order of products that track no stock); nothing is written until it is confirmed. Only what arrived is received (short deliveries leave the order **Partly received**; leaving a line out of the call takes all that is left of it), in one transaction: each line of a stock-tracked product goes in through `receiveStock` (given the outer transaction) as a `receive` movement at the ordered cost with the note "Received on PO-n"; lot number and expiry are needed for products that track them (`ReceiveLineInput`); products with tracking `none` are only recorded as bought. If any line is refused nothing is received. After receiving, the order can still be paid.
- UI: **Purchasing** group in the nav rail with **Purchases** (`pages/purchases/`: table with order/reference, supplier, date range, status and owed filters, overdue due dates in red, total owed in the header, no selection or bulk actions since orders are cancelled, not deleted) and **Suppliers** (`pages/suppliers/`, the standard table with delete/restore; a supplier owed money or with an order on the way cannot be deleted; "View purchases" opens Purchases filtered by `?supplier=<id>`). `?view-purchase=<id>` (`PurchaseViewer`) opens the order dialog (`PurchaseDetailForm`: lines, totals, record payment, edit, receive stock, cancel order) over any page. The new/edit order form (`PurchaseForm`) and the receive dialog (`PurchaseReceiveForm`) are not draftable yet.
- Seed data (`purchase.factory.ts`): four suppliers and ten orders (mostly received into the product's existing unnamed batch so stock stays consistent, some on the way, a few cancelled; paid in full, in part or not at all). The ERD has the four new tables.
- **Receive stock against an order, in parts:** `stock_movements.purchase_order_line_id` ties a receipt to the order line it was delivered against; **what has arrived of a line is the sum of those receipts** (`receivedMilli`). Receive stock (opened from the Inventory page, or from an order's dialog by **Receive by item**, which goes to `/items/inventory?receive-order=<id>` where the dialog opens with that order chosen (the parameter is then removed); the Purchases page header has no Receive stock button) has an optional **Purchase order** field (orders still waiting for stock): choosing one lists its own products with something still to come (products that track no stock included, marked Not tracked), with a note saying so ("Showing only products on PO-n"; clear the order to receive anything else), shows "Ordered n · received n · n left", and starts quantity and cost at what is left and the ordered cost (a scan of a product not on it is refused). `receiveStock` refuses a line that is not that product's, an order already received or cancelled, and more than is left. When everything ordered of the stock-tracked products has arrived the order becomes received by itself (`settlePurchase` in `queries/purchase-receipt.ts`; products that track no stock never hold it back). Until then it shows as **Partly received**; such an order cannot be edited or cancelled (its lines carry receipts), and "Receive the rest" in its dialog takes only what is left. Receive another keeps the order chosen for the next product.
- Not built yet: refunds from a supplier, cancelling an order with money paid on it, per-supplier statements.

## Checkout order draft

- The order in progress saves itself: every change to the lines is written (debounced 300 ms, flushed when the page closes) through `window.micropos.checkout.*` to the `settings` table under the key `checkout.draft` (`electron/db/queries/draft.ts`, `CheckoutDraftService` in Angular). It is restored when Checkout opens, including after an app restart. The main process validates whatever the renderer sends before storing it.
- In the ERD (`docs/erd.mmd`) the draft appears as the `checkout.draft` row of `settings`, with a dashed link to `products` (its lines hold product ids as JSON, with no foreign key). If drafts move to real `open` orders, update the ERD in the same change.
- It is one draft per register for now. Once employees sign in, move it to an `open` order (with its lines) per employee.
- **Clear vs Void:** *Clear* empties a cart that was never recorded and deletes the draft (confirmation dialog, no trace kept). *Void* is for a sale that was already recorded: it keeps the order with status `voided` and writes an audit entry so the books still add up (built: see Sales Orders). The checkout button is Clear.

## Banner (short status messages)

- Use `BannerService` (`src/app/core/banner/`) for brief feedback instead of inline text: `banner.success('Bananas added')`, `banner.warning(msg, { duration: 'long' })`, `banner.error(...)`, `banner.info(...)`, or `banner.show(msg, { severity, duration, key })`. One thin strip at the top of the window (`BannerHost`, placed once in the root); click it to dismiss.
- Default duration is 1.5 s; presets `short` 0.8 s, `default` 1.5 s, `long` 4 s, `persistent` (stays until clicked or `dismiss()`), or any number of milliseconds. Default severity is `info`.
- **Persistent banners** (`duration: 'persistent'`, e.g. an impending update notice) are kept apart from the queue and stay until the system calls `banner.remove(key)` (or `dismiss()` / a click, unless `dismissible: false`). Timed banners show over them for their moment and the persistent one returns. While one exists, `reserveSpace()` is true and the app root sets `--banner-offset` (2.25rem): the root pads down by it, the nav rail starts below it, and any page that sizes itself to the viewport must use `calc(100svh - var(--banner-offset,0px) - ...)` so nothing hides behind the strip.
- Messages queue and show one at a time (at most 5 waiting; the oldest waiting ones are dropped). Pass a `key` for anything that can repeat quickly: the same key updates the banner on screen and restarts its timer instead of queueing again.
- The banner and the "window too small" overlay are popovers in the browser top layer so they sit above dialogs; both use `keepOnTop` (`core/viewport/top-layer.ts`) with a `data-top-layer-priority` (overlay 2, banner 1). Any new always-on-top element needs a priority too, or the elements will keep re-raising each other.
- Severity colors (`success`, `warning`, `destructive`, `primary`) come from `@micropos/theme` tokens.

## On-screen keyboard

- Settings > "On-screen keyboard" (off by default, per device) turns it on; "Numpad beside keyboard" adds a numpad to the right of the QWERTY keyboard. Both live in `AppSettings` (a new setting needs a default and a `storage.migrations.ts` entry).
- It is attached at the lowest level: `OnScreenKeyboardService` (`core/keyboard/`, started in the root `App`) listens for focus on the whole document, so **no per-field code is needed**. Every `text`, `search`, `email`, `url`, `tel`, `password` input and every `textarea` gets the QWERTY keyboard (number row on top, one-shot Shift, Enter, Done). Every `type="number"` input, and any input with `inputmode="decimal"` or `"numeric"`, gets the numeric keypad (`core/keypad/`).
- Both float next to the focused field (below, else above, right or left, whichever fits; they are pushed back into view instead of clipping), as overlays in the top layer. Their keys never take focus from the field (kiosk focus rule) and edit it at the caret, firing `input`; Done blurs the field, which is what commits it. While open, the field's `inputmode` is set to `none` so an OS soft keyboard does not appear too.
- Number inputs are switched to `type="text"` while the keypad is up (a number field cannot show a half-typed "3.") and back afterwards; the keypad takes its limits from the field: `step` sets the decimals (none: whole numbers, `any`: 3), `max` sets the whole digits. `change` fires on close if the value changed. There is no minus key yet.
- Opt a field or container out with `data-no-keyboard`. To set digit limits explicitly on a text field use the `appOnScreenKeypad` directive (`[keypadWholeDigits]`, `[keypadDecimals]`); it marks the field `data-keypad` so the global service leaves it alone. Prefer the plain attributes (`type="number"`, `step`, `max`, `inputmode`) and let the service handle it.
- When adding a field, just use a normal input; check it in the app with the setting on.
